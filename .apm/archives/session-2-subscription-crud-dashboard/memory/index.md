# APM Memory Index

## Memory Notes

- Child-table RLS follows the same `auth.uid() = <owning-column>` shape as the self-keyed `profiles` table, just keyed on a distinct `user_id` FK column instead of the table's own PK — this is the template for every future user-scoped table (usage logs, invoices, etc.).
- When a resource has both a collection-scoped extra route (e.g. `GET /subscriptions/analytics`) and a `/{id}` detail route on the same prefix, the extra route's router must be registered before the CRUD router so it doesn't get shadowed by the `/{id}` path — a routing-order detail to remember when adding more `/subscriptions/*` or similarly-shaped routes later.
- The backend pytest suite mints real Supabase test users (Auth Admin API) for RLS/auth tests. Running the **full suite** intermittently fails a different live-DB test each time (observed: `test_auth`, `PATCH /me`, RLS-denial, list-filter — each passes cleanly in isolation/reruns of just that test). This is consistent with Supabase's known free-tier auth-API rate limiting (already flagged in Session 1 for outbound email) extending to the Admin API under back-to-back test-user creation, not a code defect. Treat a full-suite run with 1-3 failures (that vanish on isolated rerun) as this known flakiness, not a regression — don't chase it as a bug unless a *specific* test fails consistently in isolation.
- **Prod Supabase migration history had drifted from CLI truth** — a manual dashboard SQL fix applied to `profiles` in a prior session was never recorded in `supabase_migrations.schema_migrations`, which would have made a blind `supabase db push` fail on `CREATE TABLE profiles: relation already exists`. Fixed once via `supabase migration repair --status applied <version>` (records as applied without re-running SQL) before Task 3.1's push. Prod history is consistent now, but the underlying cause — manual dashboard schema edits bypassing the CLI — can recur; prefer CLI migrations exclusively going forward, and if a manual dashboard fix is ever truly necessary again, immediately reconcile it with `migration repair` in the same session rather than leaving drift for a future deploy to discover.
- The Supabase CLI's "linked project" is global local state, not per-command — after Task 3.1 linked it to **prod** (`ylwjevannrlsauegwbas`) to push the subscriptions migration, any future local `supabase` CLI command (including routine dev migrations) will target prod until someone explicitly runs `supabase link --project-ref zocfhyysnvptxktqezfk` to switch back to dev. Worth checking `supabase link` state before any future migration work in this repo.

- This project's shadcn/Base UI preset (`base-nova`) ships no generated `form` wrapper component — use the `field`/`separator` primitives for form UI, with `react-hook-form` + `zod` + a resolver installed separately (the Rule to use react-hook-form + Zod still applies, only the backing primitive differs from a typical shadcn setup). Also: API money fields (Pydantic `Decimal`) serialize as JSON strings, not numbers — `Number(...)` at every display/format boundary.
- When a design principle is established for one field of an aggregate endpoint (here: "group by currency, never convert"), audit that it's applied *consistently* across every field of the same endpoint — Task 1.3's `top_expenses` was the one field that silently didn't follow the same per-currency rule the rest of the endpoint used, and it shipped as a bug that surfaced only once real multi-currency data existed (Task 2.3's seeded test scenarios). Worth a deliberate check at review time whenever an endpoint mixes several similarly-shaped aggregate fields.
- **Dev servers left running across Task boundaries are fragile to Manager-side git operations.** Twice this session a running dev server broke silently (white screen / stale behavior) because a later Manager action pulled the ground out from under it: removing a merged worktree killed a Vite server still running from that directory, and a long-lived `uvicorn` process (no `--reload`) kept serving pre-fix code after a merge landed a bug fix. Neither was caught until the User actually looked at the running app. Lesson: before removing a worktree, check for live processes still running from it; after merging a fix that a running backend needs to reflect, proactively restart it rather than waiting for the User to notice stale behavior.
