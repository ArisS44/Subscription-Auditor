# Task 1.3 - Analytics Endpoint + Money Normalization

## Summary
Implemented `GET /subscriptions/analytics` and the pure money-normalization helper: active-only, cycle-normalized, per-currency roll-ups (monthly burn, annual projection, top expenses, upcoming renewals, spend-by-category), with 8 tests. Full suite green (39 passed).

## Details
- **Pure helper** (`app/services/analytics.py::monthly_equivalent`): converts `(price, billing_cycle)` to a monthly-equivalent `Decimal` (weekly ×52/12, monthly ×1, quarterly ÷3, yearly ÷12). Single source of the normalization factor; full precision, rounded to 2 places only at the response boundary.
- **SQL vs Python tradeoff (documented):** Postgres does the grouping/summing (`GROUP BY currency, category, billing_cycle → SUM(price)` in `app/db/analytics.py`), and the factor is applied per bucket in Python — exploiting that `monthly_equivalent` is linear in price, so normalizing a summed bucket equals summing per-row normalized values. Keeps the factor in exactly one place (no duplicate SQL CASE). Top-expenses is ranked in Python because its sort key *is* the factor.
- **Per-currency grouping, never FX conversion:** totals reported as `{currency: amount}`, no cross-currency mixing, no external FX dependency.
- **Active-only** everywhere; **empty portfolio** returns well-formed empty dicts/lists.
- **Endpoint/model:** `app/routers/analytics.py` (`GET /subscriptions/analytics`), `app/models/analytics.py` (AnalyticsResponse + TopExpense/UpcomingRenewal/CategorySpend). Analytics router registered in `main.py` before the CRUD router so `/subscriptions/analytics` resolves ahead of `/{sub_id}`.
- Explained the SQL-vs-Python and per-currency-vs-FX reasoning to the User before building (teaching cadence); logged both in `docs/LEARNING_LOG.md`.
