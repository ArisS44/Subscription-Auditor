# Task 3.1 - Apply Subscriptions Migration to Production Supabase

## Summary
Applied `20260707113207_create_subscriptions_table.sql` to the production Supabase project (`ylwjevannrlsauegwbas`) and verified the table, RLS, four policies, indexes, and CHECK constraints landed correctly. A prod migration-history drift was discovered and reconciled before the push.

## Details
Work was User-driven (real prod credentials; only the User can run the CLI/dashboard against prod). Steps:

1. **Dependency integration:** Read the migration file — confirmed it matches the producer summary (14 columns; three CHECK-constrained enums `category`/`billing_cycle`/`status`; `price >= 0`; RLS enabled with four `auth.uid() = user_id` policies; two `(user_id, …)` indexes).
2. **Environment check:** CLI was linked to dev (`zocfhyysnvptxktqezfk`); `backend/.env` holds dev credentials only (no prod creds in this environment), so verification was done via the prod dashboard SQL editor rather than a direct connection.
3. **Link to prod:** User ran `supabase link --project-ref ylwjevannrlsauegwbas` (succeeded).
4. **Pre-push inspection surfaced drift:** `supabase migration list` showed the **Remote column empty for both** migrations. Prod introspection revealed `supabase_migrations.schema_migrations` **did not exist** and the only public table was `profiles`. Diagnosis: `profiles` had been created manually via dashboard SQL last session, so the table existed but was never recorded in migration history — a plain `db push` would have re-run `CREATE TABLE profiles` and aborted before reaching subscriptions.
5. **Reconcile (not a blind push):** User ran `supabase migration repair --status applied 20260704152946`, which created the history table and recorded profiles as applied **without re-running its SQL**. `migration list` then showed profiles in both Local and Remote, subscriptions in Local only.
6. **Push:** After resolving the known keychain access-token gap (`export SUPABASE_ACCESS_TOKEN=…`), `supabase db push` applied **only** `20260707113207_create_subscriptions_table.sql`. (A Docker-daemon warning about caching the local pg-delta catalog is cosmetic and does not affect the remote push.)
7. **Verify:** Single-row introspection query against prod confirmed all expected structure.

## Issues
None unresolved. Two transient obstacles handled during execution: (1) the known CLI keychain access-token gap, fixed with `export SUPABASE_ACCESS_TOKEN`; (2) prod migration-history drift, fixed with `migration repair` (see Important Findings).

## Important Findings
Production had **migration-history drift**: the `profiles` table existed physically but was absent from `supabase_migrations.schema_migrations` (the history table did not even exist), because `profiles` was applied manually via the dashboard last session rather than through the CLI. This meant prod had never had a successful `supabase db push`. A blind push would have aborted on `CREATE TABLE profiles` ("relation already exists") before applying subscriptions. Resolved with `supabase migration repair --status applied 20260704152946`. Prod migration history is now consistent with the local migrations, so future `db push` operations to prod should behave normally. Manager should be aware for any subsequent prod migrations and consider whether the manual-dashboard practice should be retired in favor of CLI-only migrations to prevent recurrence.

Side effect: the Supabase CLI is now linked to **prod**; returning to dev work requires `supabase link --project-ref zocfhyysnvptxktqezfk`.
