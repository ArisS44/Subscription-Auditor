# Task 3.2 - Auth Flows & Protected Page

## Summary
Implemented the full Supabase Auth surface (signup with email verification, email/password login,
Google OAuth, password reset, logout, remember-me session persistence), a protected-route guard, and
a Hello-user page fetching the authenticated user's email from the backend `GET /api/v1/me`. Added
config-driven CORS to the backend so the browser can call it cross-origin. All validation criteria
passed, including a full manual walkthrough by the User against the real dev Supabase project.

## Details
1. **Backend CORS** (`backend/app/main.py`, `backend/app/config.py`, `backend/.env.example`): added
   `cors_allow_origins` setting (parsed to a list via `cors_allow_origins_list`) and `CORSMiddleware`,
   added last so it's outermost of all middleware — preflight `OPTIONS` requests are answered before
   reaching the per-IP rate limiter. `allow_credentials=False` since auth is a Bearer token, never a
   cookie. Verified with `ruff`/`black`/`pytest` (10/10 existing tests still pass) and a manual curl
   preflight + unauthenticated-GET check confirming `access-control-allow-origin` on both responses.
2. **Supabase client** (`frontend/src/lib/supabase.ts`): added a custom storage adapter keyed on an
   `auth-remember-me` flag, routing session storage to `localStorage` (persistent) or `sessionStorage`
   (cleared on tab close) depending on the login form's checkbox state, set via `setRememberMe()`
   immediately before `signInWithPassword`/`signInWithOAuth`.
3. **Auth context** (`frontend/src/features/auth/auth-context.ts` + `AuthProvider.tsx`): subscribes to
   `supabase.auth.onAuthStateChange` as the single source of truth for session state, seeded by an
   initial `getSession()` call; exposes `{ session, loading }` via context/`useAuth()`.
4. **Protected route guard** (`ProtectedRoute.tsx`): renders nothing while `loading` (avoids a
   redirect flash during the async session-restore gap), otherwise renders children or
   `<Navigate to="/login">` with the attempted location in `state.from` for a post-login bounce-back.
5. **Auth pages** (`frontend/src/routes/auth/`): `Login.tsx` (email/password + remember-me checkbox +
   Google button), `Signup.tsx` (shows a "check your email" state on success rather than assuming
   confirmation), `ForgotPassword.tsx` (`resetPasswordForEmail`), `ResetPassword.tsx`
   (`updateUser({ password })`, relies on the recovery-link session Supabase establishes via
   `detectSessionInUrl`). All strings keyed through `en`/`el` locale files under a new `auth.*`
   namespace. Added shadcn `Input`, `Label`, `Checkbox` components alongside the existing `Button`.
6. **Hello page** (`frontend/src/routes/Dashboard.tsx` + `frontend/src/hooks/useMe.ts`): `useMe` wraps
   `apiFetch('/me', { accessToken })` in a TanStack Query hook keyed on the access token; the page
   renders "Hello, {email}" from the *backend's* response (not the client session), proving the
   JWT→JWKS→RLS path, plus a logout button (`signOut` + navigate to `/`).
7. **Vitest**: added `vitest`, `@testing-library/react`, `@testing-library/jest-dom`,
   `@testing-library/user-event`, `jsdom`. Switched `vite.config.ts` to `vitest/config`'s
   `defineConfig` and added a `test` block (jsdom environment, a setup file for jest-dom matchers, and
   test-only `VITE_*` env values so importing `src/lib/supabase.ts` doesn't throw under test). Wrote
   one smoke test mocking `@/lib/supabase` to verify `ProtectedRoute` redirects an unauthenticated
   session to `/login`. Wired `npm run test` → `vitest run`.
8. **Env + manual verification**: copied `SUPABASE_URL`/`SUPABASE_ANON_KEY` from the already-configured
   `backend/.env` into a new `frontend/.env.local` (gitignored, never committed) rather than asking the
   User to re-enter values that already existed. Started the local backend (`uvicorn --reload`) and
   frontend (`npm run dev`) and confirmed autonomously: build, lint, `npm run test`, and CORS
   preflight/401 responses. The User then walked the full interactive cycle in a browser: signup →
   email verification → email/password login → protected page shows their real email from `/me` →
   password reset → Google OAuth login (confirmed via an incognito window, landing on
   `accounts.google.com` before returning) → unauthenticated redirect to `/login` → logout. One false
   alarm during the walkthrough: a signup attempt against an email that already had an account (via a
   pre-existing Google-linked user) produced no error and no email — this is Supabase's deliberate
   email-enumeration protection (fake-success response on a duplicate signup), not a bug; resolved by
   testing with a fresh address.
