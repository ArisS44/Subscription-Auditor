# Task 4.2 - CI/CD & First Production Deploy

## Summary
Both GitHub Actions workflows are live and green, the first real production deploy succeeded, and the
full production Definition-of-Done auth cycle passed end-to-end after fixing three real bugs surfaced
during the walkthrough: a missing SPA navigation fallback, an unmigrated prod database schema, and an
unconfigured prod Google OAuth provider.

   reported Partial, Manager merged `feat/cicd-first-deploy` → `main` (`8ab5bb1`), both workflows went
   green on that first real run.
3. Confirmed prod health check (`{"status":"ok"}`) and full security-header set on the live backend.
4. **Blocker 2 (resolved):** mid-DoD-walkthrough, direct-loading/refreshing a client-side prod route

   frontend, so the static host had no SPA fallback rule. Added

6. **Blocker 4 (resolved, DB migration):** authenticated `/api/v1/me` returned `500` in prod. Captured the
   live traceback via `az containerapp logs show --follow`:

   accounts do not, since the trigger only fires on new `auth.users` inserts).
7. **Blocker 5 (resolved, dashboard-only):** Google OAuth returned
   `{"code":400,"error_code":"validation_failed","msg":"Unsupported provider: provider is not enabled"}`
   in prod. The Google provider was configured in dev's Supabase project but never enabled/configured in
   prod. Guided the User to: generate a new Google OAuth Client Secret (the old one was no longer
   viewable, per Google's current policy), add the prod project's callback URL as an additional
   Authorized Redirect URI on the same existing Google Cloud OAuth client (shared between dev and prod),
   and enable the Google provider in prod Supabase with the Client ID + new secret. Since the old secret
   was disabled, also updated dev's Supabase Google provider with the same new secret so dev Google login
   wasn't broken by the rotation. Confirmed working in prod (with an expected few-second scale-to-zero
   cold-start delay on first call).
8. Ran the full production Definition-of-Done auth walkthrough with the User (see Validation) — all
   steps passed. Password reset failed on a retry attempt with "Could not send the reset link"; diagnosed

9. Appended CI/CD and production-deploy concepts to `docs/LEARNING_LOG.md` (Session 6 continuation):

## Important Findings
- **GitHub's `workflow_dispatch` requires the workflow file on the default branch** — the merge to `main`
  is the actual trigger mechanism for any first run, not a step that can follow validation. Relevant to
  any future CI workflow changes.
- **The Static Web App had no SPA navigation fallback at all until this Task's fix** — every client-side
  route beyond the root would have 404'd on direct load/refresh for any user, in any browser. Recommend
  treating "hard refresh on a non-root prod route" as a standing regression check for future frontend
  deploys.
- **Prod database schema was never migrated before this Task** — Task 4 provisioned infrastructure only;
  nothing had run `supabase/migrations/*` against the prod project until this Task's DoD walkthrough
  surfaced the gap via a live 500. Any future new environment/project needs an explicit
  migration-application step; it isn't implied by infrastructure provisioning.
- **Prod Google OAuth provider was never configured** — same class of gap as the migration: dev and prod
  are fully independent Supabase projects, and *every* per-project auth/provider setting from earlier
  sessions (Site URL, Redirect URLs, OAuth providers) needs its own explicit setup in prod, not just an
  allowlist entry.
- **Google Cloud OAuth Client Secrets are no longer viewable after creation** — if lost, a new one must be
  generated, and doing so requires updating *every* Supabase project (dev and prod both) sharing that
  OAuth client, or the ones not updated silently break.
- **Supabase's default email service is unsuitable for real production user volume** — a known, deferred
  gap (needs custom SMTP + a verified domain the User doesn't have yet). Worth surfacing early in whatever
  future session addresses custom domains, since it blocks reliable auth email at any real scale.
