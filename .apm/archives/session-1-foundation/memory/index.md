# APM Memory Index

## Memory Notes

- **User-scoped data-layer pattern (architectural, reuse in every session):** all per-user DB access goes through `backend/app/db/rls.py` `rls_connection(claims)` — acquires a pooled asyncpg connection, opens an explicit transaction, sets `role=authenticated` and `request.jwt.claims` via parameterized `set_config(..., is_local=true)`, then yields the connection. Postgres RLS (`auth.uid() = id`, where `auth.uid()` reads the `sub` claim) is the enforcement wall. `SET LOCAL`/`set_config(...,true)` silently no-ops outside a transaction and the query then runs as superuser bypassing RLS — always inside the transaction. New user-scoped tables follow the same per-operation RLS policy pattern keyed on `user_id`/`id = auth.uid()`.
- **Supabase JWTs for this project are ES256 (asymmetric/JWKS), NOT HS256.** Verify via `PyJWKClient` against `<SUPABASE_URL>/auth/v1/.well-known/jwks.json` (audience `authenticated`, issuer `<SUPABASE_URL>/auth/v1`). `SUPABASE_JWT_SECRET` in `.env` is unused — do not build HS256 verification. See `docs/adr/0001-jwt-verification-via-jwks-es256.md`.
- **This environment is IPv6-only-incapable:** Supabase's "Direct connection" DB host is IPv6-only and unreachable here. Always use the **Session pooler** `DATABASE_URL` for direct Postgres access (local and in-container).
- **Supabase free-tier email sending rate-limits after ~2 normal signups.** For automated test/seed users, use the **Auth Admin API** (`POST <SUPABASE_URL>/auth/v1/admin/users`, service-role key, `email_confirm: true`) and clean up after (cascade-delete removes `profiles` rows).
- **Rate limiting is currently in-memory/per-process** (`limits` lib in ASGI middleware, chosen over `slowapi` because slowapi enforces after dependency resolution and would miss 401'd auth requests). It does not coordinate across replicas — needs a shared store (e.g. Redis) once the backend scales horizontally. Decide alongside the APScheduler single-owner concern (both need shared state at scale; flagged for pre-Session-5).
- **Supabase CLI layout:** migrations/config live at repo-root `supabase/` (`config.toml` + `migrations/`), not `infra/supabase/` (which is a vestigial empty scaffold). Point any migration tooling/CI at `supabase/`.
- **Constant-time compare helper** exists at `backend/app/security/compare.py` (`constant_time_equals`) — not yet called; use it for the extension-token hash check in the browser-extension session.
- **Solo developer, live-teaching mode is a hard requirement.** Prefer sequential single-Worker dispatch over parallel fan-out so the User can absorb teaching in one chat at a time; offer parallelism but don't force it. User has been running one Worker chat at a time.
- **Supabase projects:** dev `zocfhyysnvptxktqezfk`, prod `ylwjevannrlsauegwbas`. One real Google-authenticated user exists (the User's own account).
- **Frontend stack (from 3.1):** React **19** (not spec's 18 — create-vite default), Tailwind **v4** (CSS-first, `@tailwindcss/vite`, no `tailwind.config.js`), shadcn/ui `nova` preset on **Base UI** (`@base-ui/react`, polymorphism via `render` prop) NOT Radix (`asChild`) — new shadcn components must use the Base UI API. Dark default via `class="dark"` on `<html>`. `src/lib/api.ts` `apiFetch(path, { accessToken })` attaches `Authorization: Bearer`; `src/lib/supabase.ts` is a configured `@supabase/supabase-js` client reading `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY`.
- **Pre-commit baseline (from 1.2):** `.pre-commit-config.yaml` with pinned hooks — ruff/black scoped to `backend/`, gitleaks secret scanning, hygiene hooks, and **eslint/prettier as `repo: local` `language: system` hooks** that shell into `frontend/node_modules/.bin`. Those two frontend hooks **silently skip if `frontend/node_modules` is absent** (fresh clone / CI without `npm install`) — preserve the local-hook pattern if editing the config; don't switch to mirror hooks (they can't see the flat-config plugins). `pre-commit` itself was installed via `uv tool install pre-commit` → `~/.local/bin` (not on default PATH; `export PATH="$HOME/.local/bin:$PATH"` or `uv tool update-shell`).
- **Frontend auth architecture (from 3.2, reuse in later sessions):** `features/auth/AuthProvider.tsx` subscribes to `supabase.auth.onAuthStateChange` (seeded by `getSession()`) as the single source of truth, exposing `{ session, loading }` via `useAuth()`. `features/auth/ProtectedRoute.tsx` renders nothing while `loading` (avoids redirect-flash) then guards. Authenticated backend calls use `apiFetch('/me', { accessToken })` wrapped in a TanStack Query hook (`hooks/useMe.ts`) keyed on the access token — pattern for all future authenticated data fetching. Remember-me is a custom Supabase storage adapter switching `localStorage` vs `sessionStorage`. Auth is always Bearer JWT in the header (never cookies).
- **Backend CORS (from 3.2):** config-driven `CORSMiddleware` in `backend/app/main.py`, outermost so it answers preflight before the rate limiter; `allow_credentials=False` (Bearer, not cookies); origins from `cors_allow_origins` setting / `CORS_ALLOW_ORIGINS` env (default `http://localhost:5173`). **Stage 4 deploy must add the prod Static-Web-Apps origin**, and add the prod app URL to Supabase Auth redirect allowlist.
- **Supabase anti-enumeration behavior:** a duplicate signup (email already registered, e.g. via a Google-linked account) returns a fake-success with no error and no email — intentional, not a bug. Relevant to onboarding/signup UX in later sessions.

- **CI/CD pipeline (Session 1, `.github/workflows/backend.yml` + `frontend.yml`):** trigger on `push` to `main`, path-filtered (`backend/**` / `frontend/**` + each workflow's own file), both also expose `workflow_dispatch`. Azure auth is **OIDC federated** (Azure AD app reg `gh-actions-subscription-auditor`, `AZURE_CLIENT_ID 0f7bb807-d6d0-490f-8bfc-1db047668522`, federated credential trusting `repo:ArisS44/Subscription-Auditor:ref:refs/heads/main`; roles `AcrPush` on ACR + `Container Apps Contributor` on RG) — no standing secret. backend.yml: pytest (against **live dev** Supabase — the suite is non-hermetic, needs `DEV_SUPABASE_*` + `DEV_DATABASE_URL` secrets) → build/push image to ACR → `az containerapp update`. frontend.yml: lint/test/build with `PROD_VITE_*` baked in at build → deploy `dist` to SWA via `AZURE_STATIC_WEB_APPS_API_TOKEN`. **`workflow_dispatch` cannot run a workflow until it exists on the default branch — so merging to `main` IS the trigger for the first run and for any CI-config change.**
- **Dev and prod Supabase are fully independent projects — infrastructure provisioning does NOT carry over per-project app config.** Discovered in prod via live 500s/errors during the Session-1 DoD walkthrough. For ANY new environment, each of these needs an explicit, separate step: (1) **apply `supabase/migrations/*`** to the project (prod had never been migrated — `profiles` didn't exist → `UndefinedTableError`; only new signups after applying get the auto-created row via the trigger); (2) **Site URL** (separate field from the Redirect-URL allowlist — if left at the local `http://localhost:3000` default, confirmation/reset emails link to localhost); (3) **Redirect URL allowlist**; (4) **OAuth providers** (the Google provider must be enabled/configured per project). None of these are implied by Azure provisioning.
- **Google Cloud OAuth Client Secrets are not viewable after creation** (Google policy). If lost, generate a new one — then update **every** Supabase project sharing that OAuth client (dev AND prod), or the un-updated ones silently break. Dev + prod here share one Google OAuth client (prod callback added as an extra Authorized Redirect URI).
- **Azure Static Web Apps needs an explicit SPA navigation fallback** or every non-root client route 404s on direct-load/refresh. Fixed with `frontend/public/staticwebapp.config.json` (`navigationFallback` → `/index.html`, excluding `/assets/*` and static extensions; Vite copies `public/` into `dist/`). **Standing regression check for any future frontend deploy: hard-refresh a non-root prod route.**
- **Supabase's default email service is rate-limited and unsuitable for real production auth-email volume** (hit during Session-1 testing on password reset). Real fix = custom SMTP (e.g. Resend/SendGrid) + a verified sending domain — **scheduled into Session 7 (Polish & Production Hardening)** together with the custom-domain purchase it depends on (both added to `docs/APM_SESSIONS.md` Session 7 scope). Blocks reliable auth email at scale until then.
