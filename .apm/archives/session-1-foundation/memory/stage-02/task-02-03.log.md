# Task 2.3 - JWT Verification & RLS Data Layer

## Summary
Implemented Supabase JWT verification (JWKS/ES256, not the assumed HS256), a shared asyncpg pool with a per-request RLS transaction helper, a protected `GET /api/v1/me`, security-headers middleware, per-IP rate limiting, and a constant-time-compare helper — with a passing pytest suite proving both the authorized and cross-user-denied paths.

## Details
Verified the real signing algorithm before writing any verification code: minted a pre-confirmed test user via the Auth Admin API, signed in, and inspected the issued token's header — `alg: ES256`, not HS256. Followed the token per the Task Prompt's instruction accuracy note; `SUPABASE_JWT_SECRET` is unused by this implementation. Recorded as `docs/adr/0001-jwt-verification-via-jwks-es256.md`.

Built layered from the bottom up: `app/db/pool.py` (shared `asyncpg.Pool`, created/closed via FastAPI lifespan) → `app/db/rls.py` (`rls_connection()`, the per-request RLS transaction helper) → `app/db/profiles.py` (parameterized row fetch by id) → `app/services/profile.py` → `app/routers/me.py`. `app/deps.py` holds JWT verification, factored into a plain `verify_token(token)` function (used directly by tests) wrapped by the FastAPI dependency `get_current_claims` (header extraction + generic 401 on any failure).

The RLS helper uses `set_config(name, value, is_local=true)` inside an explicit `asyncpg` transaction rather than raw `SET LOCAL ...` text, so the claims JSON is passed as a bound parameter (`$1`) instead of being interpolated into SQL — satisfies "all queries parameterized" for this statement too, not just the data queries.

Rate limiting is custom `BaseHTTPMiddleware` (`app/middleware/rate_limit.py`) using the `limits` library's `MemoryStorage`/`FixedWindowRateLimiter` directly, not `slowapi`. Investigated `slowapi` first (added, then removed) — its decorator-based limiter runs as part of the route handler body, which executes only *after* FastAPI resolves dependencies; a request rejected by the JWT dependency (401) would never reach the decorator, so repeated invalid-token requests would never trip the limiter. Plain ASGI middleware runs before routing/dependency resolution, so it sees and counts every request regardless of downstream outcome.

Test-writing surfaced two real bugs before they became latent test flakiness, both fixed:
- An async test calling `rls_connection()` directly (no HTTP) failed with "Future attached to a different loop" — the pool created via `TestClient`'s lifespan lives on Starlette's portal-thread event loop, not pytest-asyncio's. Added a separate `db_pool` fixture (`tests/conftest.py`) that creates/closes the pool directly on the test's own event loop for non-HTTP DB-layer tests.
- The tampered-signature test flipped the *last* base64url character of a real signature and the token still verified. Root cause: a 64-byte ECDSA signature isn't a multiple of 3 bytes, so its last base64 character encodes some unused padding bits — flipping only those bits can decode to the identical signature bytes. Fixed by tampering a middle character instead, where every encoded bit is significant.

Ran `ruff`, `black`, and `mypy` after the test suite passed; fixed two ruff findings (`raise ... from err` on the 404 path, `# noqa: B008` on the standard FastAPI `Depends(...)` default-arg idiom) and applied `black` formatting.

## Validation
`pytest`: 10/10 passing, re-run twice with no flakiness observed. Covers: `/health` 200; valid JWT → `/me` 200 with own email; missing/malformed/tampered-signature tokens → 401 generic (`test_missing_token_returns_generic_401`, `test_malformed_token_returns_generic_401`, `test_tampered_signature_returns_generic_401`); cross-user RLS denial via the actual `rls_connection`/`get_profile_by_id` path (`test_cross_user_read_denied_by_rls`) — this is the critical assertion and it exercises the real DB, not a mock; security headers present on responses; rate limiter returns 429 beyond the configured per-minute threshold. All test users minted/deleted via the Auth Admin API. `ruff check`, `black --check`, and `mypy` all clean.

Not separately tested: a token with a genuinely expired `exp` under a *valid* signature — would require either waiting out a real token's lifetime or a private key we don't hold to forge one. The tampered-signature test exercises the same generic-401 code path (`jwt.decode` raising a `PyJWTError` subclass, caught identically regardless of which check failed), so this is a coverage gap in exhaustiveness, not in the security property itself.

## Issues
None blocking. Two issues found and fixed during test-writing are documented above (event-loop mismatch, base64 padding-bit tamper) since they'd otherwise reappear as confusing flakiness for whoever touches this test suite next.

## Important Findings
- **`SUPABASE_JWT_SECRET` is not used.** This Supabase project issues ES256 (asymmetric/JWKS) tokens, not HS256. The Task Prompt's dependency context assumed HS256 based on the secret's presence in `.env`; verified otherwise against a real token before implementing. See ADR 0001. Any future Task assuming HS256 verification for this project's tokens should be corrected.
- **Rate limiting is in-memory/per-process**, not shared across replicas (noted as a code comment in `rate_limit.py` and in the Learning Log). This mirrors the scheduler single-owner concern already flagged in `CLAUDE.md`'s non-negotiables — worth deciding alongside that when horizontal scaling is actually introduced, since both need a shared store (e.g. Redis) at that point.
- Chose `limits` directly over `slowapi` for rate limiting (added and then removed `slowapi` after finding its decorator-based enforcement runs after dependency resolution, so it wouldn't catch repeated invalid-token requests to an auth-adjacent endpoint). No other Task/agent depends on `slowapi`, so this shouldn't affect anything else, but flagging since it deviates from what a reasonable reader might expect for "the" FastAPI rate-limiting library.
