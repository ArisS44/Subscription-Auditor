# Task 2.1 - Supabase Projects, Schema & Auth Config

## Summary
Created the dev/prod Supabase projects, authored and applied the `profiles` migration (RLS + signup trigger) to dev, configured Google OAuth and email confirmation, and verified everything end-to-end including the core RLS cross-user denial check.

## Details
Walked the User through creating `subscription-auditor-dev` (ref `zocfhyysnvptxktqezfk`) and `subscription-auditor-prod` (ref `ylwjevannrlsauegwbas`), with Data API disabled, auto-expose-new-tables disabled, and automatic RLS enabled at project-creation time. Populated `backend/.env` from the template with dev credentials; confirmed gitignored via `git check-ignore`.

Installed the Supabase CLI (`brew install supabase/tap/supabase`, v2.109.0) and ran `supabase init`, which created a top-level `supabase/` directory (config.toml + migrations/) — the CLI's standard, non-configurable layout. This diverges from the `infra/supabase/.gitkeep` placeholder scaffolded by the Infrastructure Agent; kept the CLI convention since it's what `supabase db push`/CI/all tooling expect by default, and documented the divergence in `docs/DECISIONS.md`.

Authored `supabase/migrations/20260704152946_create_profiles_table.sql`: `profiles` table with the exact spec'd columns, RLS enabled with four policies (SELECT/INSERT/UPDATE/DELETE) all keyed on `auth.uid() = id`, and a `SECURITY DEFINER` trigger function (`handle_new_user`, fired via `on_auth_user_created` on `auth.users`) that auto-inserts a profile row per signup.

Linked the CLI to the dev project via a User-generated personal access token and `supabase link --project-ref ... --password ...`, then `supabase db push` to apply the migration. Verification required installing `psql` (`brew install libpq`) and switching from the dashboard's default "Direct connection" string to the "Session pooler" string, since the direct-connection host resolves only to an IPv6 address (`dig` confirmed no `A` record) and this environment lacks IPv6 connectivity.

Verified via direct SQL: RLS is actually enabled (`pg_class.relrowsecurity = true`), the trigger exists on `auth.users`, and — using the Auth Admin API to create two pre-confirmed throwaway test users (regular signup hit Supabase's free-tier email rate limit) — that each signup produced exactly one `profiles` row. Ran the RLS cross-user check inside an explicit `BEGIN; SET LOCAL role authenticated; SET LOCAL request.jwt.claims ...; ...; COMMIT;` block simulating user A's JWT: confirmed user A can read their own row, gets 0 rows querying for user B's row, and sees only 1 row on an unfiltered `SELECT * FROM profiles`. (First attempt at this check ran the `SET` statements outside a transaction, which silently no-ops for `SET LOCAL` and caused the query to run as superuser bypassing RLS entirely — caught this from a CLI warning before drawing any conclusion, and redid it correctly.) Deleted both throwaway users afterward; confirmed cascade-delete also removed their `profiles` rows.

Guided the User through creating a Google Cloud OAuth client (Web application type, redirect URI `https://zocfhyysnvptxktqezfk.supabase.co/auth/v1/callback`) and enabling the Google provider + email confirmation in Supabase Auth settings. Verified the full OAuth flow live by having the User open `https://zocfhyysnvptxktqezfk.supabase.co/auth/v1/authorize?provider=google` directly, sign in with their real Google account, and confirmed independently via SQL that a new `auth.users` row appeared with `provider: google` and that the signup trigger fired for this OAuth-based signup too (not just email/password).

Updated `docs/DECISIONS.md` with the minimal-schema divergence note (only `profiles` created this session, not the full data model) and the CLI-layout deviation. Created `docs/LEARNING_LOG.md` (did not previously exist) with entries for Supabase, RLS, Postgres triggers/`SECURITY DEFINER`, the CLI migration workflow, JWT secret vs. API keys, and Google OAuth.

## Compatibility Concerns
Supabase CLI's standard `supabase/` directory at the repo root does not match the `infra/supabase/.gitkeep` placeholder from the monorepo scaffold. Migrations live at `supabase/migrations/`, not under `infra/`. Documented in `docs/DECISIONS.md`; any future Task or tooling expecting migrations under `infra/supabase/` will need to be pointed at `supabase/` instead.

## Important Findings
- This environment (and the User's network) lacks IPv6 connectivity; Supabase's "Direct connection" database host resolves only to an IPv6 address. Any future Task connecting directly to Postgres (locally, from this machine or similar networks) should default to the **Session pooler** connection string, not "Direct connection."
- Supabase's free-tier email send rate limit is very low — normal signup (`/auth/v1/signup`) hit `over_email_send_rate_limit` after just two attempts. Automated testing/seeding of users should use the Auth Admin API (`/auth/v1/admin/users` with `email_confirm: true`) to avoid triggering real email sends.
- The exact RLS policy predicate (`auth.uid() = id`, sourced from the JWT `sub` claim) is recorded here for the backend Task that will implement `SET LOCAL request.jwt.claims` — the claims shape must match this exactly.
