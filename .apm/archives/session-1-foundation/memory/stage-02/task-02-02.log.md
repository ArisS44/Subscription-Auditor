# Task 2.2 - FastAPI Skeleton & Health

## Summary
Scaffolded the uv-managed FastAPI backend with strict routers/services/db layering, environment-driven Pydantic Settings, versioned liveness/readiness endpoints with a real asyncpg DB ping, and a working Dockerfile — all validation criteria verified directly (not assumed), including the readiness failure path and actual container runtime behavior.

## Details
Installed `uv` (Homebrew) and ran `uv init` in `backend/`, then removed its placeholder `main.py` (the real entrypoint lives at `app/main.py` per the layering structure). Added runtime deps (`fastapi`, `uvicorn[standard]`, `pydantic>=2`, `pydantic-settings`, `asyncpg`) and dev deps (`ruff`, `black`, `mypy`) via `uv add`, which generated and pinned `uv.lock`. Added `[tool.ruff]`, `[tool.black]`, `[tool.mypy]` config to `pyproject.toml` (mypy in loose mode: `disallow_untyped_defs = false`, `check_untyped_defs = true`).

Built the layered package: `app/routers/health.py` (HTTP only), `app/services/health.py` (thin wrapper, no HTTP objects), `app/db/database.py` (a minimal `ping_database()` using a short-lived `asyncpg.connect()` + `SELECT 1`, structured so the next Task can grow it into a full pool + RLS transaction wrapper without restructuring), `app/models/health.py` (Pydantic response schemas), `app/config.py` (Pydantic `BaseSettings` reading all `backend/.env.example` variable names), and `app/main.py` (FastAPI app, health router mounted under `/api/v1`).

Per this Task's explicit dependency note from Task 2.1, corrected `backend/.env`'s `DATABASE_URL` from the direct-connection (IPv6-only) string to the session-pooler string before wiring the DB ping.

Verified locally: `uv run uvicorn app.main:app` boots; `GET /api/v1/health` → 200; `GET /api/v1/ready` → 200 with `database: up` against the real dev DB. Tested the failure path explicitly by temporarily swapping in a bad `DATABASE_URL`, confirming `GET /api/v1/ready` → 503 with `database: down`, then restored the correct value and confirmed the restoration. Ran `ruff check`, `black --check`, `mypy app` — all passed after one line-length fix.

Authored `backend/Dockerfile` (python:3.12-slim base, `uv` binary copied from `ghcr.io/astral-sh/uv`, lockfile-first layer caching) and `backend/.dockerignore`. Docker Desktop wasn't running; started it (`open -a Docker`, polled until the daemon responded) and built the image successfully. Actually ran the built container (not just built it) and hit both endpoints against it to confirm real runtime behavior, not just a successful build.

**Caught and fixed a real Docker defect during this verification:** the container logs showed `ruff`/`mypy`/`ast-serialize` being re-downloaded at startup — `uv run` in the `CMD` re-syncs against `pyproject.toml` including the dev dependency group by default, silently undoing the `--no-dev` install done at build time. Fixed by adding the venv to `PATH` and invoking `uvicorn` directly in `CMD` instead of `uv run uvicorn`. Rebuilt, reran, confirmed instant startup with no re-sync and both endpoints still correct.

**Caught and fixed a pre-existing bug in the root `.gitignore`:** it blanket-ignored `uv.lock` (line 69) and every `.dockerignore` file project-wide (line 44) — both are meant to be committed (this Task's own instructions require committing `uv.lock`; the same file's comment on lock files elsewhere confirms lockfiles should be kept). Removed both over-broad rules; verified via `git status` that `backend/.env` remains correctly ignored and nothing else was affected.

## Compatibility Concerns
Fixed a bug in the shared root `.gitignore` (over-broad `uv.lock` and `*.dockerignore` ignore rules) that would have silently blocked any future Task from committing a Python lockfile or a `.dockerignore` anywhere in the repo, not just this backend. No other Task should be affected negatively — the fix only un-ignores files that were meant to be committed.

## Important Findings
- `uv run <cmd>` re-syncs the environment against `pyproject.toml` on every invocation, including the dev dependency group by default. Any Dockerfile `CMD`/`ENTRYPOINT` using `uv run` in a production image will silently reinstall dev tooling at every container start unless it's invoked with `--no-dev` or (as done here) the venv's binaries are put on `PATH` and invoked directly. Worth keeping in mind for the extension's or any other service's future Dockerfile.
- Docker Desktop was not running in this environment by default; had to be started programmatically (`open -a Docker`, then poll `docker info`) before any `docker build`/`docker run` would work. Future Tasks needing Docker in this environment should expect this same cold-start step.
- `DATABASE_URL` in `backend/.env` was still the direct-connection (IPv6-only) string left over from Task 2.1 despite that Task's own finding about it — confirms this value needs active checking, not just documentation, whenever a new Task depends on it.
