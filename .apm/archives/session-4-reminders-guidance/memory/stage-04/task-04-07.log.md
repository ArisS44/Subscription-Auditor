# Task 4.7 - Roll Renewal Dates Forward After They Pass

## Summary

The daily reminder job now advances every active subscription whose `next_renewal_date` has gone by to its
next future occurrence, before it detects what is due. That ordering is the substance of the Task and is
safe in both directions because only dates **strictly** in the past are touched. 255 tests pass on three
consecutive serial runs; every new guarantee is sabotage-verified.

## Details

**Defect confirmed as described.** `next_renewal_date` is written in exactly two places —
`services/subscription.py` at create (line 89) and update (line 140) — and nothing advances it afterwards.
`db/reminders.py`'s due-query carries `AND s.next_renewal_date >= CURRENT_DATE`, so a date slipping into
yesterday removes that subscription from the scan permanently. Every subscription would get one reminder in
its lifetime and then go silent, with no error anywhere. The line references in the Task Prompt were
accurate.

**Mechanism: advance inside the existing daily job.** Rejected alternatives, with reasons:
- *Compute on read* — the ledger keys on `(user_id, subscription_id, kind, due_date)`, so `due_date` must be
  a stable stored value. A per-request computation could shift the key under the ledger and break the
  no-duplicate guarantee just verified in production.
- *Database trigger* — triggers fire on a write. The event here is the passage of time, which no write
  accompanies.
- *Separate scheduled job* — more moving parts; the daily job already runs service-role, user-less, bounded
  and idempotent.

**Ordering: before due-detection, restricted to `< CURRENT_DATE`.** The hazard in advancing first is real
but avoidable. `compute_next_renewal_date` returns the next renewal *strictly after today*, so advancing a
subscription that renews **today** would push it a full cycle out and silently skip that reminder — the
due-query accepts `>= CURRENT_DATE`, so today's renewal is still live. Restricting the advance to strictly
past dates removes that case entirely, and then:
- it cannot skip a reminder, because a past date was already excluded from detection, so moving it forward
  removes nothing that would have been found;
- it cannot double-send, because a new date is a new ledger key that legitimately earns its own reminder
  while the existing row still blocks the old one — the case the key was designed for.

Advancing *after* detection is also correct but costs a day: a subscription going stale today would not be
reconsidered until the next run, which for a weekly cycle can mean a late reminder.

**Anchor: the stored renewal date, not `start_date`.** Both agree for an untouched subscription, but
`update_subscription` lets a user set a renewal date explicitly ("explicit user intent always wins"), and
re-deriving from `start_date` would silently discard it. Passing the stale date as the anchor to the
existing helper also handles **many elapsed cycles in one step**, since the helper walks whole cycles until
strictly after today.

**Suppression (User-decided).** Only `status = 'active'` advances. Cancelled and paused subscriptions are
not billing, so moving their date forward would assert a future charge that is not coming. Put to the User
explicitly as the one product-flavoured choice in the Task; they confirmed no roll-forward.

**Layering.** The arithmetic lives in the service layer because `compute_next_renewal_date` is a service
function — having `db/reminders.py` import from `services/` would invert the layering. The db module gained
a bounded read and one batched write (`unnest`, single round-trip), both service-role and confined to the
job's own module.

No subagents. One correction loop, described below.

## Validation

Every stated criterion is met.

- **Past date → next future date, verified in the database** (not the UI): asserted equal to
  `compute_next_renewal_date(stale, cycle, today)` and strictly greater than today.
- **Several elapsed cycles advance in one step:** a 100-day-stale subscription lands in the future, and the
  test asserts that a *single* cycle step from the stale date would still be in the past — proving multiple
  cycles were walked — while also asserting it did not overshoot (within one cycle of today).
- **Twice in succession does not skip a cycle:** run twice, the date after the second run equals the first.
- **Advanced subscription earns a new reminder while the old stays claimed:** after advancing, the
  subscription is back in the due set, `claim_delivery` on the new date succeeds, and `claim_delivery` on
  the old date returns False. This is the ledger criterion exercised end to end.
- **Cancelled and paused produce no reminders and are never advanced:** parametrised over both statuses,
  asserting the date is unchanged *and* the subscription is absent from the due set.
- **Sabotage-verified.** Dropping the `status = 'active'` filter fails both inactive cases. Widening the
  today-boundary reproduces the exact defect (`assert 2026-09-01 == 2026-08-01`) — see Issues, the first
  attempt at this sabotage was insufficient and that is itself a finding.
- **Anti-drift:** a test reads the allowed `billing_cycle` values out of the live DB CHECK and asserts the
  renewal helper handles each. Adding a cycle to the constraint without teaching the helper would otherwise
  raise mid-run for every user.
- **Full suite: 255 passed on three consecutive serial runs** (7:20 / 7:08 / 7:11), zero failures. Baseline
  247; the 8 new tests account for the delta exactly. ruff and black clean.
- **Global-job hygiene:** `isolate_renewal_dates` snapshots and restores `next_renewal_date` for every row
  the global advance could move, so the developer's own overdue subscriptions on shared dev are not
  permanently rewritten by a test run. Mirrors the existing `isolate_deliveries` precedent.

**Live end-to-end verification by the User, through the real UI and the real job endpoint.** Three overdue
subscriptions were seeded on the User's test account and confirmed visible with past dates in the
Subscriptions tab, then `POST /jobs/run-due` was triggered manually:

| Subscription | Before | After | Expected |
|---|---|---|---|
| monthly | 2026-06-22 | 2026-08-22 | 2026-08-22 |
| weekly | 2026-07-12 | 2026-08-02 | 2026-08-02 |
| yearly, 2 years stale | 2024-08-01 | 2027-08-01 | 2027-08-01 |

The two-year-stale yearly subscription is the decisive one: it landed on the next real occurrence in a
single run rather than creeping one year forward per run. A second identical trigger reported
`advanced: 0` and changed nothing, confirming idempotency against the live endpoint rather than only in
tests.

## Issues

**Correction loop worth recording — my first sabotage proved nothing.** Widening the today-boundary from
`<` to `<=` in the *read* query left the test green. The cause is that `apply_renewal_date_advances`
re-asserts the same condition in its `WHERE`, so the write refused rows the read had wrongly selected and
the behaviour stayed correct. That redundancy is deliberate and good (the write does not trust the read's
selection, which also makes it safe against a row changing status between the two), but it means a sabotage
check that breaks one wall measures the wall left standing. Breaking both produced the real failure.

## Compatibility Concerns

**The job endpoint's response shape changed.** `JobRunResult` gains `advanced`, so `POST /jobs/run-due` now
returns six counts instead of five. The field is defaulted, so existing constructors are unaffected, but the
serialized response has an extra key and `test_run_due_accepts_correct_token` failed until its expectation
was updated — correctly, since that test exists to lock the shape. The endpoint is internal and token-authed
(called by the GitHub Actions cron), and the consumer reads status codes rather than the body, so no
external contract breaks. Flagged rather than assumed.

## Important Findings

**1. Nothing on dev is currently stale, so no retroactive repair is needed there.** Measured before
committing: 66 active subscriptions, **zero** with a past renewal date and zero renewing today. This matches
the Task's note that the defect had not surfaced only because every subscription is young. **Production has
not been checked** — if any rows there have already lapsed, the first job run after deploy will advance them
automatically, and the `advanced` count in the response will show how many.

**2. The fix is only as live as the cron.** The advance runs inside `run-due`, so renewal dates are only
maintained while the daily job runs. If the scheduler is paused or fails silently, dates go stale again and
reminders stop — the same failure as before, just with a different cause. Worth considering whether the job's
own health should be observable somewhere, since its failure mode is silence in both cases.

**3. NEW — the engine has no notification batching, and live testing made that concrete.** The manual
`run-due` trigger sent **18 separate push notifications to the developer's real account in one burst** (47
active subscriptions; 13 renewing within 7 days, 33 within 30). Every one was legitimate — they genuinely
qualified under the 3-day default lead — and the burst size was inflated because this was the first run
against dev, whose ledger was empty, so months of never-sent reminders fired together. Production has its
own ledger and will not replay like that.

But the underlying design point stands independently of the burst: the engine sends **one push per
subscription**, with no grouping and no per-user daily ceiling. With 13 renewals inside a week, ordinary
steady-state days will produce three or four separate notifications. For a user with this many
subscriptions that reads as nagging rather than helping. A daily digest ("3 renewals coming up: …") would
be one notification instead of four, and would also make the per-user volume bounded by construction rather
than by how many subscriptions someone happens to own. This is a product decision for the Manager, not a
change to make inside this Task — flagging it because it is invisible from the test suite and only showed
up when real notifications hit a real phone.

**4. The `advanced` count is a useful production signal on first deploy.** A large number on the first run
would mean many subscriptions had already gone stale in production and were missing reminders; a zero
confirms the fix landed before the defect bit real users.
