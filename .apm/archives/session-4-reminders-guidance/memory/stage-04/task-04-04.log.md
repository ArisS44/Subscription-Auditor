# Task 4.4 - Rate-Limit Error Copy

## Summary
Split the three rate-limit conditions that shared one "wait a minute" message into three distinct
messages with `en`/`el` copy and tests. The hourly email limit no longer promises a one-minute wait.

## Details

The Task Prompt's structural claims were accurate. `isRateLimit` in `frontend/src/features/auth/auth-errors.ts`
collapsed HTTP 429, `over_request_rate_limit` and `over_email_send_rate_limit` onto the single key
`auth.errors.rateLimited`, and it was called from all three mappers (`signInErrorKey`, `signUpErrorKey`,
`updatePasswordErrorKey`).

Replaced the boolean predicate with `rateLimitKey`, which returns the specific key or `null`. This keeps
the three call sites to two lines each and means a future condition is added in one place. Condition
ordering is deliberate and load-bearing: `over_email_send_rate_limit` also arrives with `status: 429`, so
a status-first check would swallow the code and emit the wrong message. The bare-429 case is a third,
non-committal message rather than being folded into either named limit — when we do not know which limit
was hit, the copy should not assert how long the wait is.

Copy decisions:
- `auth.errors.rateLimited` (per-minute request throttle) keeps its existing wording — "wait a minute"
  is accurate for this one.
- `auth.errors.emailRateLimited` is new: says too many confirmation emails have gone to the address in
  the past hour, tells the user to try later rather than immediately, and points at the spam folder in
  case an earlier one already arrived.
- `auth.errors.tooManyRequests` is new: generic, no specific wait promised.

The two new Greek strings were written as part of this Task and then reviewed again under Task 4.5's
quality lens rather than being exempted from it.

## Important Findings

- **The live surface has not been exercised.** These are error paths that need a real rate limit to
  trigger, so they were not driven through the running app. Per the project's own standard, passing tests
  here are evidence the mapping is internally consistent, not that a user sees the right message. The
  email path is now much harder to trigger deliberately since production moved to Brevo.
- **User-directed work outside this batch was also completed on this branch** (see the Task 4.5 log):
  the Reports tab was made non-interactive and its route redirected, at the User's explicit request
