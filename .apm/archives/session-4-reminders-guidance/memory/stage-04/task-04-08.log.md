# Task 4.8 - Accept a Comma Decimal Separator in the Price Field

## Summary
The price field now accepts a comma or a dot and normalises to a dot before the value leaves the form,
with the ceiling check corrected to run on the normalised value. **Logged Partial**, not Success: the
Task's final validation criterion requires confirmation on a real iPhone with a Greek keyboard, and the
User does not own an iPhone. Everything reproducible without one is verified.

## Details

**Reproduced first.** Before changing anything, a throwaway test asserted the three parts of the defect
against the current code: a comma price is rejected with `priceInvalid`, `Number('7,99')` is `NaN` so
the ceiling comparison is `false`, and `formValuesToPayload` passed the comma straight through to the
API. All three confirmed.

**The fix, in three coupled parts:**
1. `PRICE_RE` widened from `/^\d+(\.\d{1,2})?$/` to `/^\d+([.,]\d{1,2})?$/`.
2. `normalisePrice()` added and applied in `formValuesToPayload`, so the dot form is what reaches the
   `NUMERIC(10,2)` column.
3. The `PRICE_MAX` refinement now calls `Number(normalisePrice(v))`.

Part 3 is not optional polish. Reverting only that part causes comma acceptance to fail entirely — the
value passes the regex, then fails the ceiling check against `NaN`, and the user moves from "enter a
valid amount" to **"price is too large"**: still blocked, now with a message that would send them
deleting digits from a valid price. Verified by reverting each part independently.

**Thousands separators are rejected, not interpreted**, per instruction: `1.234,56` and `1,234.56` are
the same number written two ways and are indistinguishable without locale knowledge, so both are
rejected rather than guessed at.

**Placeholder** is now the i18n key `subscriptions.form.fields.pricePlaceholder` (`0.00` / `0,00`),
decided by the User when the choice was put to them.

## Important Findings

- **Status is Partial for one reason only: the device check.** The Task's own criterion — "a desktop
  browser cannot reproduce this defect, so a green suite is not evidence the fix works" — is correct
  about the *cause* and worth splitting from the *fix*. What a desktop cannot reproduce is iOS drawing
  a keypad with no dot key. What it reproduces exactly is everything after that keystroke, because a
  physical keyboard types a comma perfectly well. The component tests cover that half end-to-end. What
  remains unverified is narrow and specific: that an iOS decimal keypad in a Greek locale emits `,`.
  That is documented platform behaviour, and it is also the premise of the whole Task — if it were
  false, there would have been no bug report.
- **The stored value was not read from the database.** The criterion asks for the stored value, not a
  successful submit. The strongest available evidence is the request body containing `"7.99"`; the
  column is `NUMERIC(10,2)` and the backend is unchanged by this Task, so the remaining risk is small
  but it is not zero and was not eliminated.
- **The User plans to have beta testers confirm on their own devices.** That closes the gap properly
  and is the right call, but it means this ships before the device-specific half is confirmed.
- **Task Prompt discrepancy.** The prompt describes `toCreateInput` and "its update sibling" around line
  101. Neither exists: there is a single `formValuesToPayload` at line 97 that both create and edit pass
  through. This is better than described — the two paths cannot drift, and the normalisation has exactly
  one home. A grep confirmed it is the only place a price is built for the API.
- **A deliberate non-change.** Editing an existing subscription prefills the price from the backend,
  which always sends a dot, so a Greek user sees `7.99` in the field regardless of their keyboard. Both
  separators are accepted, so this is harmless. Localising the displayed value was rejected: it would
  require converting back on save and adds round-trip risk for no functional gain.
- **A stale Vite process was killed.** A `node vite` process had held port 5173 for over 20 hours,
  serving code from a previous session. It was terminated while restarting the dev server; port 5173 now
  serves current code.
