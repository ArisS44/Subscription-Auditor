# Task 2.15 - Pre-Auth Language Switch & Onboarding Footer Simplification

## Summary
Promoted the language switcher out of the dashboard and mounted it on every pre-auth surface, carried a
pre-signup language choice into `profiles.preferred_language` (verified by reading the row, not the UI),
and removed the redundant onboarding footer Skip. Live testing then surfaced a genuine navigation bug in
the method step's skip card, which was fixed here; the User additionally directed three in-flight changes,
all delivered.

## Details

**Part A — language switch.** The prompt's premise was confirmed before changing anything: `i18n/index.ts`
registers `i18next-browser-languagedetector` with no `detection` config, so the default order applies,
`navigator` *is* consulted, and nothing is hardcoded to English. The real gap was purely that the only
control lived in the authenticated sidebar.

- Moved `features/dashboard/LanguageToggle.tsx` to `components/LanguageToggle.tsx` and added an optional
  `className`, plus a `PinnedLanguageToggle` wrapper for the pre-auth placement.
- Placement and styling were chosen by the User from three options (`AskUserQuestion` with mockups):
  **pinned top-right**, mirroring the `AuthBrand` lockup pinned top-left, on the landing page and all four
  auth routes (including Signup's separate confirmation-sent branch); **inline in the existing header** in
  the onboarding wizard, where a fixed corner element would collide with the ✕.
- Persistence: `profiles` rows are created by a database trigger (`handle_new_user`, security definer) with
  `preferred_language default 'auto'`, so the frontend takes no part in the initial insert. The choice is
  therefore applied on first authenticated load by `i18n/PreferredLanguageSync.tsx`, mounted in
  `ProtectedRoute` — the one place wrapping both `/onboarding` and `/dashboard`. It goes through
  `useUpdateProfile` (`setQueryData` then invalidate, per the onboarding-gate fix).
- Two deliberate constraints: only an **explicit click** is recorded (`i18n/language-preference.ts`), never
  a browser-detected language, since `'auto'` is meaningful server-side; and the write happens **only while
  the stored value is still `'auto'`**, so an account's own preference is never overwritten by a shared
  browser.
- The sync is a null-rendering component rather than a hook in `ProtectedRoute` because
  `ProtectedRoute.test.tsx` renders without a `QueryClientProvider`; gating it behind the session keeps that
  test valid.
- Per User decision, the toggle's labels moved from `dashboard.language.*` to a top-level `language.*`
  namespace now that the component is shared.

**Part B — onboarding footer.** Every structural claim in the prompt matched the code exactly (`StepFooter`
at line 366, both buttons bound to `onNext`, the test at line 111). Removed the Skip button and the
`onboarding.skipStep` key from both locales. The method step's separate skip card was preserved as
instructed.

**Bug found in live testing and fixed (User-reported).** After choosing "chat with Apollon" and going Back,
pressing the method step's skip card landed in the assistant instead of the reassurance screen. Cause: the
skip card called a bare `goNext` rather than `chooseMethod`, so it advanced *without recording the choice*
— it only ever looked correct because a first-time user's `method` is `null` and `SetupStep`'s fall-through
happens to be the reassurance screen. With a stale `method: 'chat'` it rendered `ChatView`. Fixed by routing
all three cards through `onChoose`, removing the asymmetry rather than special-casing it. This was necessary
to satisfy this Task's own criterion that the skip card still reaches the reassurance screen.

**User-directed changes during execution** (see Important Findings): the onboarding notification opt-in no
longer requires a subscription; its onboarding presentation was restyled after the User judged it "awful";
the Settings email hint was removed; the coming-soon placeholder was centred; and signup/login validation
was hardened.

## Compatibility Concerns
- **i18n key namespace moved:** `dashboard.language.{label,en,el}` → `language.{label,en,el}`. Any other
  Worker's in-flight branch referencing the old keys will silently render raw key strings.
- **Keys deleted from both locales:** `onboarding.skipStep`, `settings.emailHint`,
  `notifications.optIn.checking`, `notifications.optIn.needsSubscription`.
- **`LanguageToggle` moved** from `@/features/dashboard/LanguageToggle` to `@/components/LanguageToggle`.
- **`NotificationOptIn` gained an optional `bare` prop** (default `false`, so existing usage is unchanged).
- **`NotificationStep` no longer takes `accessToken`**, and `MethodStep` no longer takes `onSkip`.

## Important Findings
- **The method-step skip card was broken for any user who changed their mind** (detail above). Worth noting
  as a pattern: the bug survived because the correct-looking behaviour depended on an unrelated default
  (`method: null`) rather than on the code doing the right thing.
- **User-directed scope change, reversing a Task 2.4 decision:** the onboarding notification opt-in is now
  offered regardless of subscription count. The User's reasoning is sound — notification permission is a
  browser-level grant independent of subscription count, and the previous gate meant anyone who skipped
  adding a subscription (which the flow explicitly invites) silently never got the chance to enable
  reminders. Flagged because Task 2.4 deliberately gated it.
- **Signup/login hardening was User-directed and is not fully enforced yet.** The client policy (8+, a
  letter, a number) is **UX only** — Supabase Auth is the trust boundary, and the hosted policy still allows
  6 characters with no character requirements. **The User must set minimum length 8 + letters-and-digits in
  the Supabase dashboard for BOTH dev and prod** (separate projects) or the policy is cosmetic. Supabase's
  `weak_password` error is mapped to a readable message as a backstop.
- **Login errors are deliberately vague for bad credentials** to avoid an account-enumeration oracle;
  unconfirmed-email, rate-limit and network failures are reported precisely. Recorded so a future "improve
  the error messages" Task does not undo it as an oversight.
- **`auth.password` is a leaf string**, so the password rules had to live at `auth.passwordPolicy.*` — the
  leaf-vs-namespace i18n collision this project has hit before.
- **Nothing applies a stored `preferred_language` back to the UI on login.** The persisted value is currently
  consumed only by the backend (reminder copy, chat prompt language); it does not restore the UI language on
  a new device. Out of this Task's scope, but it limits what "the choice follows the user" delivers. Needs a
  Manager decision.
- **The confirmation email body remains in Supabase Auth's own template language**, as the prompt stated.
  Out of scope and not attempted.
