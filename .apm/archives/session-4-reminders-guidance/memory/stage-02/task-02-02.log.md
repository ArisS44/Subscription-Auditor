# Task 2.2 - Reminder Engine & Job Endpoint

## Summary

Built the channel-agnostic renewal-reminder engine and a token-authenticated `/api/v1/jobs/run-due` endpoint,
made safe to run twice by claiming each reminder in the Task-1.1 ledger before sending. 16 new tests (174
passing overall), and a live double-run against the developer's real account and device proved exactly-once:
run 1 sent 4 real Greek notifications, run 2 sent zero.

## Details

Built in strict layering, with the service-role power confined to a new job-only data module.

- **db/reminders.py** — service-role (plain pooled connection) data access, following the fx.py/usage.py
  precedent. `get_due_reminders` joins subscriptions→profiles, computes the effective lead time as
  `COALESCE(s.reminder_lead_days, p.renewal_lead_days)`, and returns active, not-yet-past, in-window
  subscriptions with no existing ledger row, ordered deterministically under a LIMIT. `claim_delivery` does
  the `INSERT ... ON CONFLICT DO NOTHING RETURNING id` (True = newly claimed, False = already handled).
  `get_active_push_subscriptions` and `delete_push_subscription` are deliberately *separate* service-role
  functions from the rls-scoped ones in db/push.py — the duplication keeps the RLS-bypassing connection
  unreachable from any user route.
- **services/reminders.py** — the engine orchestration. Claims first, then renders copy, then fans out to the
  user's devices via the mechanism-only `channel.send` (from Task 2.1), pruning `EXPIRED` and retaining
  `FAILED`, stamping `delivered_at` when at least one device accepted. It runs its own service-role
  orchestration and never calls the user-scoped `deliver_to_user`.
- **services/notifications_copy.py** — the project's first server-side localized text. `en`/`el` renewal
  title+body rendered from parameters; `resolve_language` maps `auto`/None/unknown → English.
- **routers/jobs.py** — `POST /jobs/run-due`, `X-Job-Token` compared with `constant_time_equals` (its first
  real use), fail-closed on an unset token, one identical generic 401 for missing/malformed/wrong. Does not
  use `get_current_claims` — it is token-authed and publicly routable.
- Config: `reminder_job_batch_size` (default 100) bounds the per-invocation scan.

No subagents used. One notable correction loop: see Validation.

**Teaching:** delivered the required pause on the service-role/RLS boundary before writing it — why a user-less
job legitimately needs an RLS-bypassing connection, and the three confinement rules (own data functions only,
never widened into shared helpers, never reachable from a user route), pointing at fx.py/usage.py. The
non-obvious concrete: duplicating the device-fetch query rather than reusing db/push.py's.

## Validation

- **Due detection:** in-window due; outside-window and already-past not due — asserted on `get_due_reminders`
  membership of the test subscription.
- **Lead-time precedence both directions:** a `reminder_lead_days` override includes a renewal the tight
  profile default would exclude; a NULL override inherits the profile default (proven both when the default
  includes and when it excludes the renewal).
- **Suppression:** cancelled and paused produce no due row.
- **Idempotency:** a double run of the full engine sends to the device exactly once and leaves exactly one
  ledger row; `claim_delivery` proven directly to return True then False.
- **Delivery classification:** an `EXPIRED` device is pruned; a `FAILED` device is retained.
- **Copy:** renders in `en` and `el`, `auto` → English.
- **Auth:** missing/wrong/malformed all return an identical 401 body; an unset token rejects everything; the
  correct token is accepted.
- **Full suite:** 174 passed, 0 failed on the first run — no reruns needed. 2 shared users.
- **Ruff + black clean**; pre-commit passed.

**Manual double-run proof (live, the decisive step):** with the backend running locally and `JOB_TOKEN` set,
`POST /jobs/run-due` was called twice. Run 1 returned `{"due":4,"sent":4,"skipped_already_sent":0,"pruned":0,
"failed":0}`; run 2 returned all zeros. The four subscriptions belong to the developer's own real account
(`arisskyllas2004@gmail.com`, `preferred_language='el'`), which still has the real Apple push device from Task
2.1 — so run 1 delivered four real **Greek** notifications (also proving the bilingual selection end to end),
and the ledger shows all four `delivered`. Run 2 found zero due because run 1's ledger claims filtered them
out. This is exactly-once delivery proven against real data and a real device — the single most important
production behaviour of this Task. (Notification content is deliberately absent from logs; verified the only
log output was uvicorn's own lines.)

**Correction loop worth recording:** the first test run asserted the engine's *global* counts and failed
(`due=5`), because the engine scans all users by design and shared dev holds other accounts' real
subscriptions. The fix was structural, not a loosening: due-detection tests now assert on the test
subscription's membership in the due set (non-mutating), and engine-running tests use an endpoint-aware
`channel.send` stand-in (test outcome only for the test user's endpoint, DELIVERED for everyone else, so no
real device is pruned) plus an `isolate_deliveries` fixture restoring `notification_deliveries` to its
pre-test state. The first failing run had itself written four delivered ledger rows for the real account;
those were cleaned before the manual proof.

## Important Findings

**Follow-up fix applied at User request: push TTL (commit `53ecae8`).** A User question surfaced a real
delivery gap in the Task 2.1 adapter: `pywebpush` defaults to `ttl=0` ("deliver now or discard"), so a device
asleep/offline at send time — a closed laptop — dropped the reminder entirely, and the ledger claim meant it
was never retried. `PushChannel.send` now sends `settings.push_ttl_seconds` (default 72h, env-tunable), so the
push service holds the message until the device next comes online within the lead window. A new test asserts a
positive TTL reaches `webpush`. This tightens Task 2.1's adapter; noted here because it was found and fixed
during this Task. Full suite re-confirmed green after the change.

**At-most-once semantics: a transiently-failed reminder is not retried — by design, but worth a decision.**
The engine claims the ledger row *before* sending (the mandated idempotency mechanism), and any existing claim
suppresses re-send. So if every device send fails transiently (a 5xx/timeout), the reminder is claimed but
never delivered, and it will not be retried on a later run. "Retain on FAILED" keeps the *device* for future
*different* reminders, but this specific reminder is consumed. This is the correct reading of "never
double-send" but it trades away "never miss." If the Manager wants at-least-once for transient failures, that
needs a more complex scheme (e.g. gating re-send on `delivered_at IS NULL` with a retry lease) that must not
weaken the exactly-once guarantee — out of scope here, flagged for a decision.

**The same claim-first design consumes a reminder for a user with no registered device — and will affect the
future email channel.** A due subscription whose owner has no push device is still claimed (counted `failed`),
so if they register a device later in the lead window they miss that renewal's reminder. More consequentially:
the ledger key is `kind='renewal_reminder'` with no channel dimension, so once claimed, a *second channel*
(email, a later session) is also suppressed for that renewal even though push never delivered. When email
lands, the Manager will need to decide whether the ledger should become per-channel or gate on delivery.

**Testing a globally-scoped job against shared dev is a standing hazard.** Unlike every prior table, this job
reads and writes across all users, so it interacts with other accounts' real data in dev — including the
developer's own. Tests must assert per-subscription and must not run a destructive global outcome (e.g. an
all-EXPIRED send would prune real users' devices). The pattern established here (per-subscription assertions +
endpoint-aware channel stub + ledger restore) should be reused by any future test touching this job, and is
worth a Rule if more user-less jobs arrive (the monthly-review job is coming).

**One instruction discrepancy.** The Task described claiming and then implied transient failures are retried
("retain ... try again later"); as above, retain applies to the device row, not to re-sending the claimed
reminder. Implemented the at-most-once reading the idempotency requirement demands and flagged the tension
rather than silently choosing.
