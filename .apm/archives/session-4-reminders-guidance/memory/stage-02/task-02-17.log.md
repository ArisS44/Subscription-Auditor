# Task 2.17 - Password Policy Parity on the Reset Flow

## Summary
Brought `ResetPassword.tsx` onto the shared password policy, closing a live mismatch in which the browser
accepted a 7-character password that the server (minimum 8) rejects. Signup and reset now consume a single
password-field definition, so they cannot disagree again. Verified live by the User walking the real reset
flow.

## Details

**The state found matched the prompt exactly** — `minLength={6}` at line 51, plain `useState`, no schema,
no checklist. No discrepancies to report.

- **Route rewired** to `react-hook-form` + `zodResolver` with `mode: 'onTouched'`, mirroring the signup
  route, and rendering the same `PasswordRequirements` checklist.
- **Single source of truth enforced structurally, not by convention.** Rather than writing a second schema
  that happens to match, the policy-checked password field was extracted in `auth-schema.ts` as
  `passwordField(t)` and is now consumed by both `createSignupSchema` and the new
  `createResetPasswordSchema`. Duplicating the rules is precisely how the two surfaces drifted apart in the
  first place, so the fix removes the opportunity rather than correcting the instance.
- **The hardcoded number is gone.** No `minLength` attribute remains anywhere in the auth routes;
  `PASSWORD_MIN_LENGTH` is the only place 8 appears.
- **Unicode behaviour untouched.** `\p{L}` / `\p{Nd}` are unchanged, so a Greek-letter password still
  satisfies the letter rule — which is what keeps the client compatible with the server's letters-agnostic
  policy. A test pins this (`κωδικός12` completes the reset).
- **Error mapping extended** with `updatePasswordErrorKey`, surfacing `weak_password` and `same_password`
  rather than the blanket "the reset link may have expired". The old behaviour sent a user off requesting a
  fresh link when the password was the actual problem. This slightly exceeds instruction 3, which asked
  only to keep `weak_password` in place; flagged in Important Findings.

**Non-vacuity checked.** The three rejection tests were confirmed to fail with the resolver removed, so they
pin the fix rather than passing incidentally. This follows the vacuous test caught in Task 2.16.

## Important Findings
- **The mismatch was live in production, not pending.** The Manager's correction was right and my Task 2.16
  report was wrong on this point: the Supabase minimum had already been raised to 8 on both projects, so
  every user hitting the reset form with a 7-character password was getting a server rejection the UI had
  invited. Worth noting for sequencing generally — a client-side policy and the server policy it mirrors
  should change in the same change-set, or the looser side becomes a live defect in the gap.
- **`same_password` mapping added beyond the stated scope.** Instruction 3 asked only that `weak_password`
  remain. While wiring the mapping it was clear that *every* failure previously rendered as "the reset link
  may have expired", which actively misdirects a user who simply reused their current password. Small,
  additive, and covered by the error-mapping tests, but recorded since it was not requested.
- **The two password surfaces now share one definition**, so the class of bug this Task fixed cannot recur
  by editing one surface. Any future policy change is a single edit to `password-policy.ts`. If a third
  surface is ever added (an in-app "change password" screen, for instance), it must consume `passwordField`
  rather than restate the rules.
- **The client remains stricter than the server**, deliberately: the hosted policy enforces length only,
  while the client also requires a letter and a digit. That is the safe direction the policy module
  documents, but it means a password set outside this UI (Supabase dashboard, API) can be valid server-side
  yet not satisfy the form's rules. No action needed; recorded so it is not later mistaken for a defect.
