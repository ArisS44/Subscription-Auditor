# Task 2.10 - Push Device List Endpoint

# Summary

`GET /push/subscriptions` returns the caller's registered push devices without the encryption keys, RLS-scoped
via the existing `list_for_user` service function. 211 tests pass on three consecutive full-suite runs. The
key-absence invariant was verified by sabotage in both directions, which established that the response model —
not the column list — is the load-bearing wall. One environment incident during validation, described under
Issues, cost several hours and produced no code defect.

## Details

Small and additive, as scoped. The layers beneath already existed and were **previously unused** — this route is
the first caller of both `services/push.py::list_for_user` and `db/push.py::list_subscriptions_for_response`, so
their response shape was mine to settle.

**Path choice: `GET /push/subscriptions`,** not the offered `GET /push/subscribe`. `POST /subscribe` is
verb-shaped (an action), so a GET on the same path would read as fetching that action while actually returning a
collection. No collision with the greedy `{endpoint:path}` converter on the sibling DELETE, which is a different
method and a different first segment.

**Response model: reused `PushSubscriptionResponse` unchanged.** It already carries exactly `id`, `endpoint`,
`user_agent`, `created_at` — enough for Settings to label and revoke a device, and no key fields. No extension
was needed, so the route returns `list[PushSubscriptionResponse]` with no wrapper.

**Two things added beyond the literal instruction,** both reported below: a `LIMIT` on the read query, and a
secondary `id` sort for deterministic ordering when two devices share a `created_at`.

No subagents. No correction loop on the code — it passed first run.

## Validation

Every stated validation criterion is met and verified.

- **Returns the caller's devices with the right fields:** two registered devices come back with `endpoint`,
  `id`, `created_at`, and `user_agent` present.
- **Keys never present:** asserted absent under every name they go by (`p256dh`, `auth`, `p256dh_key`,
  `auth_key`, `keys`), plus a structural test asserting `PushSubscriptionResponse.model_fields` is exactly
  `{id, endpoint, user_agent, created_at}`.
- **Verified by sabotage, in both directions** - this is what makes the invariant trustworthy rather than
  assumed:
  - Widened the *query* to select `p256dh_key, auth_key`, model untouched -> **all tests stayed green.** Pydantic
    drops unknown keyword arguments, so the response model blocks the keys on its own even when the query hands
    them over.
  - Widened the *model* to carry both keys -> **two tests turned red** (`p256dh_key must never reach this
    response`, and the field-set assertion).
  - Conclusion: the model is the real boundary, the column list is defence in depth, and the tests do detect a
    genuine leak. Both files restored and re-confirmed green afterwards.
- **Cross-user isolation with positive control:** A's own list is asserted to contain the device *first*, so B's
  empty list is a real denial rather than a query that matched nothing; A's row is then re-checked as surviving
  B's read.
- **Revocation still works:** subscribe -> list shows it -> `DELETE /push/subscribe/{endpoint}` -> list is empty.
  Consent is revocable in fact: the row is gone, not muted.
- **Auth required:** 401 unauthenticated, matching the sibling routes' convention.
- **Empty case:** returns `[]` with 200, not a 404.
- **No endpoint or key in logs:** audited every log call on this path. The three in `services/push.py` carry an
  HTTP status, an exception class name, and fan-out counts respectively. The new route logs nothing at all.
- **Full suite: 211 passed, 0 failed on three consecutive serial runs** (5:52 / 5:54 / 5:52). Previous baseline
  205; the 6 new tests account for the delta. ruff and black clean; pre-commit hooks passed.

## Issues

**Finding for the Manager - the read path was unbounded, and one sibling still is.** The Task said to use the
existing `list_for_user`, which had no `LIMIT`. Device counts are small in practice but not bounded by
*construction* — each browser profile is another row and nothing caps rows per user — so leaving it open-ended
sits against the standing "paginate every list endpoint" / bounded-work rule. I capped it at 100 rather than
adding `limit`/`offset` query parameters: full pagination on an inherently tiny owner-scoped collection would
invent API surface Settings will not use, while the cap satisfies the actual intent (bounded work per request).
**If the Manager wants literal limit/offset here for consistency with `GET /subscriptions` on the subscription
router, say so and it is a five-line change.** Separately and out of scope: `db/push.py::list_subscriptions` —
the key-carrying one used by the delivery fan-out — is *also* unbounded, and that one is on the reminder job's
path where bounded-work-per-invocation is an explicit standard. Worth a look independently of this Task.

**Environment incident during validation — no code defect, but it cost hours and I mishandled it.** The first
three-run batch went 211 passed clean, then `210 passed, 1 error` (`test_fixture_isolation.py::
test_leaves_rows_behind_for_the_next_test`, a `TimeoutError` in fixture setup, run time 7:39 vs 5:53), then the
third run hung. A replacement batch degraded far worse — 72% complete after 2h39m, with `test_rls.py` and
`test_subscriptions.py` tests failing on what were almost certainly timeouts. Postgres latency measured healthy
throughout the aftermath (~300ms connect, ~90ms query), and after the environment settled the suite ran three
times at 5:52/5:54/5:52 with identical code. So this was transient shared-dev degradation, the documented
flakiness pattern, and not a regression.

Two process errors of mine made it much worse than it needed to be, both worth recording:
1. I piped each run through `tail -6`, which emits nothing until the run completes — so a hung run is
   indistinguishable from a healthy one, and I could not see which test was stuck. Runs should stream progress
   (`-q` or `-v` without `tail`) precisely so a hang is diagnosable.
2. I reported "nothing is wrong" from a log file whose last write was 53 minutes old, without checking its
   mtime or the process elapsed time. The User caught this, correctly.

Killing the hung runs skipped the session-scoped fixture's user cleanup, orphaning 4 `test-*@example.com` Auth
users (all with zero rows, since `_reset_user_data` runs on setup). I audited row ownership *before* deleting
anything and removed exactly those 4. The developer's real account (66 subscriptions), their real Safari push
device, and their 4 genuine delivered reminders from 2026-07-24 were identified and left untouched — worth
flagging as a standing hazard of testing against shared dev: a careless "delete test-looking rows" cleanup here
would destroy real data.
