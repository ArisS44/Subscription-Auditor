# Task 2.16 - Restore a Stored Language Preference on Login

## Summary
Added the read direction to `PreferredLanguageSync`, so a stored `preferred_language` now sets the UI
language at login and the preference genuinely follows the user across devices. Verified live in all three
scenarios and read back from the database. The password-policy audit (item 6) found one real mismatch in
`ResetPassword.tsx`, reported rather than changed as instructed.

## Details

**Read direction.** On first authenticated load a stored `'en'`/`'el'` is applied to the active language,
beating i18next's browser detection. A stored `'auto'` is left untouched: it means "follow my browser", and
forcing it to a concrete language would silently discard that choice. Comparison is on the base tag, since
`i18n.language` can be a region variant (`en-US`).

**Write direction preserved.** A pre-signup choice is still promoted into a profile sitting at `'auto'`, and
an account already carrying a deliberate preference is never overwritten — in that case the leftover browser
flag is *cleared* instead, so it cannot leak onto a second account signed in from the same browser. All
writes still go through `useUpdateProfile` (seeds the `['me']` cache from the PATCH response, then
invalidates).

**How the switcher interaction was resolved (the Task's substance).** Both available options were taken,
because either alone leaves a hole:

1. *Reconcile once per mount, not per profile change.* This is what stops the sync fighting the switcher
   mid-session.
2. *Mirror a switcher change into the profile — but only when the account already stores a concrete
   `'en'`/`'el'`.*

Point 2 is not optional polish. Without it the new read direction would **actively break the switcher**:
switching to Greek would survive only until the next login, when the stored value overrode it again — a
worse defect than the one this Task fixes. The `'auto'` carve-out is what keeps this consistent with the
precedence rule: a switcher click never converts `'auto'` into a hard language, and i18next's own cache
already makes such a click persist on that browser. Implemented as an `i18n.on('languageChanged')`
subscription inside the same component rather than by giving `LanguageToggle` profile-writing powers —
`useAuth` throws without an `AuthProvider`, and the toggle also renders pre-auth and is unit-tested bare, so
pushing account knowledge into it would have broken both.

**A vacuous test, caught and replaced.** The first "does not revert" test passed even with the
once-per-mount guard deleted: the mirroring PATCH updates the cached profile to match, so nothing reverts
on the happy path. It was replaced with a test where the PATCH returns 500 — the profile keeps saying
`'el'`, so a sync reconciling on every render drags the user back. That version was confirmed to fail with
the guard removed and pass with it.

**Item 6 — password-policy audit.** `PASSWORD_MIN_LENGTH` confirmed at 8; the Unicode `\p{L}`/`\p{Nd}`
behaviour left exactly as it was. Signup requires a letter and a digit, which is *stricter* than a server
enforcing no character classes — the safe direction the file's invariant permits. One real mismatch found
and reported, not changed (see Important Findings).

## Issues
- A redundant PATCH is possible in one edge case: the Settings form changes the language immediately after
  its own PATCH, and if the profile cache has not re-rendered yet the listener may write the same value a
  second time. Guarded with a ref updated optimistically before mutating, which closes it in practice; the
  write is idempotent and same-valued, so the residual risk is a wasted request, not incorrect state.
- Dev servers ran on port **5175** (5173 and 5174 were still held by earlier sessions' servers). All three
  are in the backend CORS allowlist, so this was harmless, but stale dev servers on the lower ports serve
  old code and remain a trap.

## Important Findings
- **`ResetPassword.tsx` never received the password policy and is the one place the invariant is violated
  in the forbidden direction.** It is still plain `useState` with `minLength={6}` and no schema or
  checklist, while signup enforces 8 + letter + digit. Once the hosted Supabase minimum is set to 8, the
  browser will accept a 7-character password and the server will reject it — the client being *looser* than
  the server, which is exactly what `password-policy.ts` documents as forbidden. Reported rather than fixed
  per instruction 6; the fix is small (put the route on the existing `createSignupSchema`-style schema and
  `PasswordRequirements`) and I did not apply it. **This should be scheduled before the policy change goes
  live in Supabase**, or the reset flow becomes the weak point.
- **Two password surfaces now tell users different things.** Signup's checklist promises "at least one
  number"; reset enforces none of it. Even after the server minimum is raised, a user can set a
  letters-only password through reset that signup would have refused. Not a security hole — the server
  accepts both — but an inconsistency worth settling when the above is scheduled.
- **The in-app switcher now writes to the account** for users with a concrete preference. This is a
  behavioural change to a control that was previously local-only, and it is the deliberate answer to
  instruction 4; noted so it is not later mistaken for drift.
- Instruction 4 offered the two options as alternatives ("either is defensible"); implementing only one
  would have satisfied the letter of the criteria while leaving the switcher non-durable across logins.
  Flagged because it is a case where the stated criteria were narrower than the objective.
