# Task 2.13 - Chatbot Performance: Diagnose & Fix What's Safe

## Summary

Measurement contradicted the Task's leading hypothesis: the system prompt was not the problem. Of a
5.40s tool-calling turn, the model accounted for 1.47s and our own backend for 3.19s across **48 database
round-trips, ~30 of which fetched nothing**. Three safe reductions took round-trips to 39 and non-provider
time from 3.23s to 2.04s median (-37%), with no behavioural change. The prompt was deliberately left
untouched. User-directed follow-on work then fixed four defects that live manual testing surfaced,
including a frontend bug that displayed a €7.99 subscription as €8. 239 tests pass on three consecutive
serial runs; the live behaviour sweep passes 44/44 in EN and EL.

## Details

**Measured before changing anything.** Instrumentation wrapped `llm.stream_chat_turn` and counted every
`asyncpg` round-trip, so no production code was altered to take the measurement. The breakdown:

| Component | Cost |
|---|---|
| System prompt | 5,745 chars / 3,171 input tokens |
| Tool schemas (Gemini wire) | 7,526 bytes — *larger than the prompt* |
| `tool_definitions()` rebuild | 1.50 ms/turn |
| Empty `rls_connection` block | **181 ms** (4x a real query) |
| Provider (both calls, tool turn) | 1.47 s |
| Database (48 round-trips) | 3.19 s (59%) |
| Auto-title (serial provider call) | 0.74 s (14%) |

The cost was structural, not query-level: `rls_connection` pays BEGIN + `set_config` + COMMIT + pool reset
around every block, and a tool-calling turn opened seven blocks.

**Applied (behaviour-neutral):**
1. `chat_db.get_turn_context` — one query replacing three (conversation row, message count, language).
2. `usage_db.increment_daily_both` / `add_tokens_both` — per-user and app-wide counters in one statement.
3. Auto-title generated concurrently with the turn instead of serially after it, and persisted in the
   same transaction as the final assistant message. Event order unchanged.

**Rejected, with reasons:**
- *Condensing the prompt* — the change the Task expected. Worth ~1% of the turn against the risk of four
  rules that each fixed a live defect. Not attempted.
- *Batching message inserts* — unsafe. `messages.created_at` defaults to `now()` (transaction-start time,
  identical for rows written together) and `id` is a random `gen_random_uuid()`, so batching would make
  `get_recent_messages`' ordering non-deterministic and could replay a tool result before its call, which
  Gemini rejects. Needs an ordering column, i.e. a migration.
- *Session-scoped `set_config`* — would remove the ceremony and is a cross-user data leak. Explicitly
  ruled out by the User.
- *Reordering `enforce_caps`* — would save ~225ms by folding the velocity check into the main block, but
  changes cap semantics. Reported, not taken.

**User-directed additions after the performance work was complete and committed.** The User asked for
these; they are outside the Task's stated scope and are recorded as such.

4. **Model pinned** (`gemini-flash-lite-latest` -> `gemini-3.1-flash-lite`). The alias had re-pointed to a
   new generation mid-session. Benchmarked 10 runs each with the real prompt and all 11 tool schemas.
5. **Wrong-target guard** — the three write tools now require the model to state which name it is acting
   on; a mismatch against the stored row returns a refusal instead of a write. Word-based matching, since
   a substring test would pass "pokemon go" inside "pokemon golf".
6. **Two prompt rules** — a question is not an instruction (no write to answer "why is X uncategorised?");
   a rendered table is the answer (do not also emit markdown).
7. **Frontend money fix** — `formatNumber` capped at one fraction digit, rendering 7.99 as "8".

No subagents used. No correction loop on the code; one instrumentation error (double-counted `BEGIN`)
found and fixed before reporting any number.

## Validation

- **Latency, before/after:** round-trips 48 -> 39 (tool turn), 31 -> 22 (text turn). Non-provider time per
  turn 3.23s -> 2.04s median across the live sweep. Median turn 4.83s -> 4.10s. Chart turns now take 3
  provider calls instead of 4 (the render-tool description fix removed a guaranteed refused attempt).
- **Live behaviour sweep, EN + EL, verdicts from the database and tool-call list:** 44/44 across twelve
  behaviours, each in a fresh conversation with every touched row reset between cases.
- **Full suite: 239 passed on three consecutive serial runs** (6:53 / 6:39 / 6:36), zero failures. ruff and
  black clean; frontend 137 tests pass and `npm run build` is clean (run per the standing tsc-vs-Vitest rule).
- **Verified by sabotage, three times** — each negative assertion was broken on purpose and confirmed red:
  removing the app-wide counter branch (2 tests red), removing the wrong-target guard (wrong-target test
  red, both over-correction tests still green — proving they test different things), and restoring the
  single fraction digit (`expected '8' to be '7.99'`).
- **User manual testing through the real browser** — the decisive step. All scenarios confirmed working by
  the User after the fixes, including the money display, single table render, no-write-on-question, and the
  single "building chart" status.

## Issues

**An end-to-end before/after comparison was impossible for several hours.** Mid-Task the provider degraded
severely — a bare five-word request with none of our code involved took 17-29s, and turns reached 104s. The
"after" sweep taken in that window is unusable as a latency comparison and is reported as such rather than
presented as a result. The provider-independent metric (non-provider overhead) is what the improvement
claim rests on. A later sweep against a healthy provider gave the clean end-to-end numbers above.

**An earlier claim of mine was wrong and is corrected here.** I initially attributed the slowness to the
model alias change. Larger sampling showed 3.1 and 3.5 flash-lite are tied at ~0.5s and that *every* model
was slow in that window, including one that spiked to 54s. The alias drift is a real risk; it was not the
proven cause of the episode.

## Compatibility Concerns

**Production is still on the floating alias.** The pin covers local dev and the committed `.env.example`
only. Deployed environments set `LLM_MODEL` themselves, so production continues to run whatever
`gemini-flash-lite-latest` currently resolves to until that variable is updated — an infrastructure change,
not this branch's.

**The write tools gained a required argument.** `update_subscription`, `mark_subscription_cancelled` and
`delete_subscription` now require `subscription_name`. Any caller constructing these payloads outside the
model (tests, future code) must supply it; three existing tests were updated. Live-verified that the model
supplies it correctly in both languages and through the real HTTP/SSE path.

**Input tokens rose ~8%** (7,273 -> 7,878 per turn) from the new argument and its description. Accepted:
prefill is sub-second and the argument is what makes the guarantee structural.

## Important Findings

**1. The performance problem was ours, not the model's.** Roughly three-quarters of a turn was backend
time. Any future "the chat is slow" investigation should measure the round-trip count first; the visible
component (a long prompt) was the wrong suspect and would have cost four behavioural rules to "fix".

**2. Four defects were found only by the User's manual browser testing**, after 32 automated live scenarios
and 239 unit tests passed. Three existed only on the HTTP/SSE/render path my harness bypassed by calling
`stream_turn` directly. The most serious — money rounded to the nearest euro — was invisible from the
backend because the data was correct all the way to the database and broke at render time. Strong evidence
for the standing "prefer a live check" rule, and an argument that a chat-surface harness should exercise the
real endpoint, not the service function.

**Entered as a Rule at the User's direction.** `CLAUDE.md` (AI chatbot & LLM integration) now carries: *a
chat-surface change is not verified until it has been exercised through the real endpoint, not just the
service function* — with the concrete evidence, and a preference for the User's hands-on pass when they are
available. This applies to all Workers on the chat surface, not just this Task.

**3. `render_table` requires a `get_analytics` call even when its rows came from `query_subscriptions`.**
Listing subscriptions has nothing to do with analytics, so the grounding guard is stricter than its purpose
needs. I only made the tool description honest about it (which removed a wasted round-trip); loosening the
guard is a security-adjacent decision for the Manager.

**4. The test suite is ~70% fixture overhead.** Measured: a fresh `asyncpg.connect()` costs 301ms and
`_reset_user_data`'s seven statements cost 856ms, so ~1.16s per test before any assertion — roughly 4.6
minutes of a 6.7-minute run. Batching those seven statements into one round-trip and reusing a single
connection would plausibly halve the suite with no loss of fidelity, which matters because the standing
rule requires three consecutive runs (20 minutes) to judge any regression. Not attempted; test
infrastructure and outside this Task.

**5. The wrong-target defect is now structural, but not absolute.** The tool boundary rejects a write whose
stated name contradicts the target row. It cannot stop a model that asserts a different name on a retry,
which is why the refusal tells it not to retry and the prompt rule stays. Recorded per the standing rule
against presenting a prompt-level guarantee as structural — and the same limit applies with full force to
the two new prompt rules (findings A and B), which are reductions in frequency only.
