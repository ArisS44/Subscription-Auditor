# Task 2.1 - Push Storage, Endpoints & Sender

## Summary

Built the full backend Web Push surface — RLS-scoped storage, a mechanism-only delivery adapter with
prune-vs-retain failure classification, and subscribe/unsubscribe/dev-test routes — with 18 new tests
(158 passing overall). Live-verified: a real encrypted notification arrived on Safari/macOS via Apple's push
service, showing the exact payload body, the first genuine proof the VAPID keypair and payload encryption
work.

## Details

Built in strict `routers/` → `services/` → `db/` layering, following the existing subscriptions/chat modules.

- **db/push.py** — `upsert_subscription` (INSERT ... ON CONFLICT (user_id, endpoint) DO UPDATE, so
  re-subscribing a device refreshes rotated keys rather than duplicating), `list_subscriptions` (with keys,
  for the sender), `list_subscriptions_for_response` (without keys, for the client), `delete_by_endpoint`
  (unsubscribe), `delete_by_id` (pruning). All on `rls_connection` — this surface is entirely user-initiated,
  so the service role is never used here (that boundary is reserved for the later user-less reminder job).
- **services/push.py** — `PushChannel.send` is the delivery adapter: its only job is how to send one message
  to one device, with no reminder logic and no DB. `pywebpush` is synchronous (requests-based), so each send
  runs via `asyncio.to_thread`. A `WebPushException` whose response status is 404/410 → `EXPIRED` (permanent,
  prune); anything else → `FAILED` (transient, retain). `deliver_to_user` fans out best-effort and prunes
  dead rows as found. The `DeliveryOutcome` vocabulary is deliberately channel-neutral so an email adapter can
  reuse it. Thin `subscribe`/`unsubscribe`/`list_for_user` service functions keep the router off the db layer.
- **routers/push.py** — `POST /push/subscribe`, `DELETE /push/subscribe/{endpoint:path}` (the endpoint URL is
  matched exactly and never fetched; `:path` preserves its slashes), `POST /push/test` (returns an identical
  404 to a nonexistent route when `settings.env != "development"`). All require `get_current_claims`.
- **models/push.py** — validates the native browser `PushSubscription` shape (`{endpoint, keys:{p256dh,
  auth}}` + optional `user_agent`). Endpoint validated as http(s) and length-capped; keys constrained to the
  base64url alphabet and capped. `user_id` is never a client field.

Registered the router in `main.py` under `/api/v1`.

**No subagents used; no correction loop.** The only mid-build diagnostic was confirming the new FastAPI
(0.139) represents included routers as lazy `_IncludedRouter` objects, so `app.routes` does not show flattened
paths — verified registration via `app.openapi()` instead.

**Teaching:** delivered the required pause on the Web Push encryption model before coding — the two distinct
key systems (VAPID authenticates the sender to the push service; p256dh/auth encrypt the payload to the
device), what the push service can and cannot see, and why a 410 is a lifecycle event to prune rather than an
error to retry.

## Validation

- **Subscribe persists scoped to caller; repeat subscribe upserts (no duplicate):** asserted via API and
  directly in the DB.
- **Unsubscribe removes the row; unknown endpoint → 404:** asserted.
- **Failure classification:** a mocked 410 deletes the row (`pruned=1`); a mocked 500 and a `TimeoutError`
  both leave it in place (`failed=1, pruned=0`); a mixed 410+success fan-out prunes only the dead one and
  keeps the live one. `pywebpush` mocked at the module boundary — no real push service contacted in tests.
- **Dev-only test endpoint:** 404 when `settings.env="production"`, 200 in development, 401 unauthenticated.
- **No secrets in logs:** proven by a capture harness — a forced failure produced only
  `push delivery failed status=500`; the endpoint, both keys, and the body were asserted absent from all log
  output.
- **Cross-user isolation:** B cannot see or delete A's rows, with a positive control proving A's row exists
  first (not a vacuous pass).
- **Full suite:** 158 passed, 0 failed on the first run — no reruns needed. Counter confirmed 2 shared users.
- **Ruff + black clean**; pre-commit hooks passed.

**Live verification (User-performed, the decisive criterion):** the User registered a real browser
subscription and sent a test. Result `{"total":1,"sent":1,"pruned":0,"failed":0}` (HTTP 200), and a macOS
notification appeared reading exactly "Test notification — your push setup is working." — the byte-for-byte
`NotificationPayload.body` from the router. The stored endpoint was `https://web.push.apple.com/...`, so this
went through Apple's push service on Safari/macOS: the encrypted payload was delivered and correctly decrypted
by the device. This proves both key systems end to end — VAPID authentication accepted by the push service
AND payload encryption readable by the device — which is exactly what the static "keys are placed" checks
could not establish. (Screenshot evidence provided by the User; not copyable into the repo as the Desktop is
outside the tool sandbox, so the result is transcribed here.)

## Important Findings

**The VAPID pipeline is now proven working, which closes the open risk flagged from Infra Task 1.3.** The
keypair provisioned there was confirmed only *placed*; this live send is the first evidence it actually works,
and it does — against Apple's push service, the strictest target. Subsequent push work (the reminder engine)
can treat the transport as trusted.

**Dependency pinning convention differed from the instruction.** The Task said to pin `pywebpush` to an exact
version, but this project pins with `>=` in `pyproject.toml` and lets `uv.lock` hold the exact version. I
followed the project's actual convention (`pywebpush>=2.3.0`, locked to 2.3.0 in `uv.lock`) per the
Instruction Accuracy note, rather than introducing a lone `==` pin.

**A live-test harness exists but is uncommitted.** The self-contained subscribe page was necessary because
the frontend has no subscribe flow yet (a later Frontend Task). It embeds the public anon key and VAPID public
key (both non-secret by design) and currently lives in the job scratch dir. If the Manager wants it retained
for re-testing push before the real frontend flow lands, it should be committed under a devtools path;
otherwise it is disposable. Raising rather than committing it unilaterally, since it is throwaway UI outside
the Task's stated output.

**Delivery/composition seam is in place for the next channel.** `PushChannel` is mechanism-only and
`DeliveryOutcome` is channel-neutral, so the later email channel and the reminder engine can reuse the adapter
without changing it — but note `deliver_to_user` is deliberately user-scoped orchestration (reads/prunes the
caller's own rows under RLS). The reminder job is user-less and must supply its own service-role orchestration
around the same `PushChannel`, not call `deliver_to_user`.
