# Task 2.8 - Expose Lead-Time Fields Through the API

## Summary

`profiles.renewal_lead_days` is now readable and writable through `/me`, `profiles.monthly_review_enabled` is
readable but not writable, and `subscriptions.reminder_lead_days` is accepted on create/update and returned on
read with NULL preserved as "inherit". Range validation (0-30) mirrors both DB CHECKs. 205 tests pass on three
consecutive full-suite runs. One schema finding for the Manager: both profile columns are nullable rather than
`NOT NULL`, which the specified non-nullable response shape assumes.

## Details

Small and additive, as scoped. RLS, the reminder engine, and unrelated fields are untouched.

**Profile.** Added `renewal_lead_days: int` and `monthly_review_enabled: bool` to `ProfileResponse`, and
`renewal_lead_days` to `ProfileUpdate`. `monthly_review_enabled` is absent from `ProfileUpdate` **and** from
`_UPDATABLE_COLUMNS` - the read-only guarantee is those two absences, each independently sufficient, with the
allowlist load-bearing because it filters column names so a client key can never become SQL.

An explicit `"renewal_lead_days": null` is rejected with a 422. This is not in the Task text but follows from
it: the profile value is what a subscription's NULL inherits via the engine's COALESCE, so a NULL there leaves
nothing to resolve to. A Pydantic field validator expresses it cleanly because validators do not run for unset
fields - "omitted" stays a valid no-op, "explicitly null" is a clean 422. Note the deliberate asymmetry with
the subscription field, where NULL *is* the meaningful value.

**Subscription.** Added `reminder_lead_days` to `SubscriptionCreate`, `SubscriptionUpdate`,
`SubscriptionResponse`, the shared `_COLUMNS` constant, `_UPDATABLE_COLUMNS`, and the INSERT parameter list.
The service passes it through untouched so an omitted or explicitly-null value stores NULL rather than being
coerced to a number.

**Shared type.** The 0-30 bound mirrors two separate DB CHECK constraints that must agree, so `LeadDays` lives
once in a new `backend/app/models/common.py` rather than as a duplicated literal in two models.

**Two deviations from the letter of the Task, both reported below:** the explicit-null rejection above, and
extracting a `_COLUMNS` constant in `db/profiles.py`. The profile column list was written out twice (SELECT and
`UPDATE ... RETURNING`); adding two fields to one copy and not the other is exactly the drift
`db/subscriptions.py` already guards against with its own `_COLUMNS`, and the Task instructs following the code
where it differs. Adopting the existing pattern beat adding a third copy.

No subagents. One correction loop (see Issues).

## Validation

Every stated validation criterion is met and verified.

- **Profile persistence:** `PATCH /me` with `renewal_lead_days: 7` returns 7 and a fresh `GET /me` returns 7
  (asserted against the fixture's reset default of 3, so the change is real).
- **Read-only `monthly_review_enabled`:** readable as `true`; a `PATCH` attempting `false` returns 200 (Pydantic
  drops the unknown key) with the stored value unchanged, confirmed by a subsequent `GET`.
- **Not vacuous - verified by sabotage.** A "cannot write this" test passes just as greenly if it tests
  nothing, so I temporarily added `monthly_review_enabled` to both `ProfileUpdate` and `_UPDATABLE_COLUMNS` and
  confirmed **both** tests turned red (`assert False is True`), then restored and re-confirmed green. Sabotaging
  both walls at once is the right check here precisely because either alone is sufficient.
- **Inherit vs override:** creating without the field stores NULL (not the profile's number); creating with 10
  returns 10 and round-trips on read; updating to 1 then explicitly to `null` both work, confirmed by a fresh
  `GET`; an unrelated `PATCH` leaves an existing override intact (omitted vs explicit-null survives the trip).
- **Reaches what the engine reads:** a service-layer test sets a profile default of 4 and an override of 9, then
  asserts the engine's own `COALESCE(s.reminder_lead_days, p.renewal_lead_days)` resolves to 4 and 9
  respectively - the exposure is only worth anything if the values land in the columns the job reads.
- **Range rejection:** 999, -1, and the boundary 31 are all 422 on profile update, subscription create, and
  subscription update.
- **Model-facing surface:** the chat tools reuse these models directly, so `add_subscription` with
  `reminder_lead_days: 6` persists 6, omitting it yields None, `update_user_settings` persists a profile
  default, out-of-range values are rejected before execution, and the model cannot flip
  `monthly_review_enabled`.
- **Full suite:** **205 passed, 0 failed on three consecutive serial runs** (352s / 342s / 342s), per the
  project's noisy-flakiness rule. Previous baseline was 193; the 12 new tests account for the delta. ruff and
  black clean; pre-commit hooks passed.
- **RLS unchanged, engine untouched:** no migration, no policy change, no edit to `db/reminders.py` or
  `services/reminders.py`.

Nothing here required live verification beyond the DB - these are HTTP and DB round-trips the suite exercises
against real dev Supabase, not a structurally-unverifiable surface.

## Issues

**Finding for the Manager - both profile columns are nullable, not `NOT NULL`.** The Task specifies
`renewal_lead_days: int` and `monthly_review_enabled: bool` on `ProfileResponse`, which assumes the columns
cannot be NULL. The profiles migration declares them `int default 3` and `boolean default true` with **no
`NOT NULL`**, so a NULL in either would make `GET /me` fail response validation and return a 500. I checked dev
empirically: 14 profile rows, zero NULLs in either column, and `information_schema` confirms
`is_nullable = YES` for both. So the specified shape is safe today, and I closed the write path so the API
cannot introduce a NULL (`monthly_review_enabled` is unwritable; an explicit null `renewal_lead_days` is a 422).
The residual risk is a NULL arriving by some other route. The clean fix is a `SET NOT NULL` migration, which
this Task explicitly excludes ("no migration is needed - this is API-layer work only"), so I did not write one.
**Recommend a follow-up migration** adding `NOT NULL` to both columns, plus the `renewal_lead_days` CHECK the
column lacks entirely (`subscriptions.reminder_lead_days` has one; the profile column does not, so its 0-30
bound currently rests on Pydantic alone with no DB backstop - a genuine gap in the two-walls standard).

**Side effect worth an explicit decision: the chat agent gained these fields automatically.** The tool registry
reuses `SubscriptionCreate` and `ProfileUpdate` as tool argument schemas, so exposing a field on the API exposes
it to the model in the same edit. The user can now say "remind me a week before" with no tool change, which
reads as the registry design paying off, and the fields are benign (a small bounded integer, no PII, no
destructive effect). But it means the API model is the trust boundary for an untrusted caller too, so the range
bound is what stops a model-produced `999` from reaching the DB. Tested on that surface. Flagging it because it
widens the model's write capability without a Task line item asking for it - if the Manager wants the chat
surface to *not* carry these fields, that needs separate tool-specific arg models.

**Correction loop (one).** My first version of the COALESCE test used both the `test_client` and `db_pool`
fixtures and failed with `InterfaceError: another operation is in progress`. The cause is documented in
`conftest.py`: TestClient's pool lives on Starlette's portal-thread event loop while `db_pool` is on
pytest-asyncio's, and the two must not be mixed. Rewrote it to drive the service layer directly - the HTTP
surface is already covered by the sync tests - and recorded the reason in the test's docstring. The same run
surfaced a pre-existing direct `insert_subscription` call in the RLS test needing the new keyword argument;
updated.
