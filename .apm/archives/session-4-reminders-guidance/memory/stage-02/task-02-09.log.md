# Task 2.9 - Strict Frontend Content-Security-Policy

## Summary
Added a strict Content-Security-Policy (plus two hardening headers) to the served frontend via Static Web Apps `globalHeaders`, scoped to exactly what the app loads, and verified it live with the CSP actually enforced — login incl. Turnstile, chat SSE, push registration, and normal traffic all clean with zero console violations.

## Details
- **Enumerated loads empirically from the code** (browser automation was unavailable in this session): the only external host is Cloudflare Turnstile (`challenges.cloudflare.com`, injected `<script>` + widget iframe — `frontend/src/features/auth/Turnstile.tsx`); the chat stream is a `fetch`/SSE to the API origin (`chat-stream.ts`), not EventSource; fonts are self-hosted Geist (`/assets/*.woff2`); no `data:` image URIs in `src`; the built `index.html` has no inline `<script>` (only the external self module) and no inline event handlers.
- **Policy** in `frontend/public/staticwebapp.config.json` `globalHeaders`: `default-src 'self'`; `object-src 'none'`; `base-uri 'self'`; `frame-ancestors 'none'`; `form-action 'self'`; `script-src 'self' https://challenges.cloudflare.com`; `frame-src https://challenges.cloudflare.com`; `connect-src` = `'self'` + dev API (`http://localhost:8000`) + dev Supabase + **prod** API (`https://ca-subscription-auditor-backend.nicebush-826aba8d.germanywestcentral.azurecontainerapps.io`) + **prod** Supabase (`https://ylwjevannrlsauegwbas.supabase.co`); `worker-src 'self'`; `manifest-src 'self'`; `img-src 'self' data:`; `font-src 'self'`; `style-src 'self' 'unsafe-inline'`. Also `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`. No `unsafe-eval`, no wildcard sources.
- **`style-src 'unsafe-inline'` rationale:** the UI libraries (Recharts, the component primitives) set inline `style` attributes at runtime; a strict style policy without it breaks rendering, and the toolchain does not nonce styles. This is scoped to styles only — `script-src` gets no such allowance, so it does not permit code execution. This was the one genuinely unavoidable relaxation.
- **Prod origins** confirmed from the running infra (`az containerapp list` → `ca-subscription-auditor-backend...azurecontainerapps.io`; prod Supabase from the User), not assumed. Both dev and prod origins are in the single committed policy so it is correct in either environment. The CORS allowlist being set to the SWA origin confirmed the browser calls the Container App cross-origin (a separate `connect-src` entry), not same-origin.

With the CSP enforced and the console open, the User exercised login + Turnstile CAPTCHA, a streaming chat reply, push subscription registration, and dashboard/API navigation: **"clean"** — no CSP violations. (An initial run on `:4280` produced CORS preflight 400s — a port/allowlist mismatch, not a CSP issue — resolved by serving on an allowlisted port.)
- `npm run build`: clean. `npm run test`: 131 passing (unchanged — CSP is a static header, no code impact).
- Served header re-verified to include both prod origins in `connect-src`.

## Issues
- **Prod enforcement is not exercised locally** — the local build points at dev origins, so only the dev flows were enforced-tested. The prod `connect-src` entries are the actual deploy targets (confirmed from infra), so the policy is correct by construction; final prod enforcement is naturally confirmed on the Stage-3 deployed build. `http://localhost:8000` remains in the committed `connect-src` (needed for dev) and is harmless in prod (a prod browser never calls localhost).
