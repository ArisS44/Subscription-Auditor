# Task 2.11 - Chat Anti-Fabrication for Lead Times & Ambiguous-Match Confirmation

## Summary

Both live defects are fixed in the identity prompt and verified against the real model in EN and EL. A missing
reminder lead time is now asked for rather than invented; a subscription reference that is not one of the user's
actual subscription names now triggers a "which one do you mean?" question instead of a silent edit to the
closest name. The ambiguous-match rule required a second wording iteration — the first draft passed every
text-presence test and was still disobeyed in English. 227 tests pass on three consecutive full-suite runs.

## Details

Surgical prompt refinement, as scoped — two paragraphs in `_APOLLON_IDENTITY`, no restructuring.

**1. Lead times added to the never-invent rule.** The existing sentence forbidding invented prices, billing
cycles, and dates was left **byte-identical** (its wording is asserted by Task 2.3's tests) and extended with a
following clause covering reminder lead times, naming both `renewal_lead_days` and the per-subscription
override in plain language. It states that a vague comparative — "earlier", "sooner" — must never be read as
implying a number. Deliberately worded to sit in the same category as price/date and to contrast with the
category-is-classification rule, which is unchanged.

**2. New "Targeting the right subscription" paragraph.** Placed before the tool-hiding rule and explicitly
marked as separate from, and additional to, the destructive-action confirmation discipline — it governs *which*
subscription an action lands on, and applies to non-destructive edits.

**The wording iteration is the substance of this Task.** The first draft said to act only when the user's words
"clearly and unambiguously identify exactly one" subscription. It passed every prompt test and was **obeyed in
Greek but not in English**: asked to change the price of "Pokemon golf", the model edited "Pokemon go" from
€4.99 to €30.00. The inference it made is reasonable and is exactly the defect — with only one similar name in
the account there is no ambiguity from the model's point of view, so "unambiguous" was satisfied. The abstract
criterion delegated the decision back to the judgement that was already wrong. The second draft makes the
name comparison primary and names the excluded case outright: *"you must ask which one they mean ... EVEN IF
exactly one of their subscriptions looks similar. Being the only similar name does not make it the intended
one."* That held.

Preserved unchanged and re-asserted by tests: grounding, the Task 2.7 current-date directive, the Task 2.3
category-classification rule, tool-name hiding, the financial-advice refusal, and the destructive-action
confirmation discipline.

No subagents. Two correction loops (see Issues).

## Validation

**Prompt-level:** 42 prompt tests pass, including tests locking in both new rules and tests asserting the five
preserved rules are intact.

**Live model verification — the deliverable, since text-presence proves only that the words are present.**
Driven through `chat_svc.stream_turn` (the real engine, real model), each scenario in a **fresh conversation** so
no history bled between cases, with verdicts read from the **database and the tool list** rather than the
model's prose, which will claim a successful edit either way.

All four required behaviours confirmed in **both EN and EL**:

| Behaviour | Result |
|---|---|
| Missing lead time ("remind me earlier about Netflix") | Asks "How many days before the renewal...?"; no write tool fired; `reminder_lead_days` stayed NULL |
| Given lead time ("remind me 7 days before") | `update_subscription` fired; `reminder_lead_days = 7` in the DB |
| Near-miss name ("Pokemon golf") | Asks "Did you mean Pokemon go?"; no write tool; price unchanged at 4.99 |
| Clear match ("change Netflix to 15.99") | Edits directly, no confirmation step; price 12.99 -> 15.99 in the DB |

**Stability re-check, because a single pass on a stochastic model proves little:** the two risk scenarios were
repeated **3x each per language — 12/12**. This deliberately included the **over-correction guard**: a rule that
made the model confirm before every ordinary edit would trade a wrong-target defect for a friction defect, so
"clear match must still edit directly" was measured, not assumed (6/6).

**Full suite: 227 passed, 0 failed on three consecutive serial runs** (5:43 / 5:54 / 6:31). ruff and black clean;
pre-commit hooks passed.

## Issues

**Important finding - a prompt rule can hold in one language and fail in another.** The first wording was
obeyed in Greek and disobeyed in English on the same scenario, same model, same turn structure. Had the live
check been run in one language only — or had EL been checked first — the defect would have looked fixed and
shipped. Any future prompt-behaviour change on this surface must be verified in **both** languages, and the
bilingual live check should be treated as the minimum bar rather than thoroughness. This is a stronger claim
than the existing "live-verify prompt changes" standard and is worth adding to it.

**Related finding for the Manager: the fix is prompt-level only, which is a real limit.** Both defects are now
prevented by instruction, not by construction. The model still *has* an unrestricted `update_subscription` tool
that accepts any `subscription_id` it chooses, so nothing structurally prevents a wrong-target write — a
sufficiently confused turn can still do it, and no test can prove otherwise. A defence-in-depth option, if the
Manager wants one later: have the update path require the target name to match the stored name, or return a
disambiguation error to the model when a name lookup is inexact, so the guarantee lives in code rather than in
wording. Out of scope here and not attempted.

**Correction loop 1 (test wording, twice).** My prompt-test assertions broke twice on line wrapping — the prompt
hard-wraps at ~76 cols and my chosen fragments straddled line breaks, so they could never match. The test file's
own header comment warns about exactly this and I walked into it anyway. Fixed by printing the assembled prompt
and selecting fragments that sit on one line.

**Correction loop 2 (live harness state).** The first live run's reset helper restored only Netflix's price, so
when the English near-miss scenario wrongly changed Pokemon go to €30.00, the Greek scenario ran against the
corrupted baseline and reported a meaningless before/after. Its verdict happened to remain correct, but only
incidentally. Fixed to restore every row the scenarios touch before each case — the same per-case reset
discipline the pytest fixtures use.
