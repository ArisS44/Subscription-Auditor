# Task 2.3 - Service Guides & Guidance Tool

## Summary

Seeded `service_guides` with 18 curated services (user-agreed list), registered `get_subscription_guide`
through the tool registry with a two-tier curated/unverified provenance model, and corrected two Apollon
prompt rules (cancellation guidance now in scope; category is classification, not fabrication). Verified live
against Gemini in EN and EL; 184 tests passing. Live testing surfaced a separate pre-existing date-resolution
defect (below).

## Details

- **Seed migration** `20260724160000_seed_service_guides.sql` (data-only, idempotent via
  `ON CONFLICT (service_key) DO UPDATE`): 18 services across streaming/ai_tool/productivity/cloud_storage,
  agreed with the User first. Accuracy over breadth — `cancel_url` set only where the destination is stable
  and verified (10 of 18); in-app/on-device flows (ChatGPT, Claude, Notion, Figma, 1Password, iCloud on
  device) carry steps with a NULL url rather than a guessed link. `plans` left NULL deliberately: prices
  change and are financially material, the same fabrication risk this Task tightens against. Applied to dev
  only; history verified clean before and after.
- **db/service_guides.py** — read-only lookup on `rls_connection` (the table's authenticated-read RLS grants
  the SELECT; it has no user write policy, so a read cannot mutate). Matches by exact slug OR case-insensitive
  display_name, both bound parameters. No write function exists — seeding is migration-only.
- **services/guides.py** — the two-tier trust logic. Curated hit → `provenance=curated` with the real
  cancel_url carried as data. Miss → `provenance=unverified`, `cancel_url=None`, and a note instructing the
  model to give general guidance without asserting a specific URL as verified. JSONB columns are parsed to real
  lists (asyncpg returns them as strings here). The backend never fetches either URL.
- **tools.py** — `get_subscription_guide` registered via `ToolSpec`+`register()` only; the chat loop and
  `dispatch` are untouched (the standing `test_adding_a_tool_is_registration_not_a_core_edit` still passes).
  Args model is a single `service: str` field so the Gemini schema rewrite has nothing exotic to trip on.
- **prompts.py** — narrowed the financial-advice refusal so concrete cancellation guidance for the user's own
  subscriptions is explicitly in scope while generalised financial/investment advice stays refused; split the
  anti-fabrication rule so price/billing/date are still never invented but category is assigned by
  classification against the five-value taxonomy (preferring a curated guide's category). Grounding,
  tool-name-hiding, and destructive-confirmation rules unchanged.

No subagents; one small correction loop (JSONB returned as string → parse in the service).

## Important Findings

**Live testing surfaced a real, separate date-resolution defect — chat-added subscriptions with relative
dates are stored wrong.** When told "add Netflix ... started today" (real date 2026-07-24), the model set
`start_date` to **2025-05-18** — its training-cutoff notion of "today" — in BOTH languages. The category fix
worked, but the model has no knowledge of the actual current date, so any relative date ("today",
"yesterday", "last month") is silently corrupted on chat-created subscriptions, and the downstream
next_renewal computation inherits the wrong anchor. This is NOT caused by this Task (the prompt never supplied
the current date) and was invisible to unit tests; the live pass caught it. A fix would inject the current
date into the system prompt (or expose it via a tool). Flagged for the Manager as a follow-up — it affects
data correctness of chat-added subscriptions, which is the primary write path.

**Dependency-pin/reference-data discrepancy resolved as instructed.** The Task suggested modelling seeding on
"how existing reference data (e.g. fx_rates) is populated," but `fx_rates` is populated lazily at runtime, not
seeded — there is no existing data-seed migration to mirror. Used a standard data-only migration (the Task's
stated alternative), applied to dev only. No impact.

**Guidance reads are user-path, not service-role.** The Task framed curation writes as needing a service-role
path "the same way you handled the reminder job's writes." In this Task there are no runtime writes at all —
seeding is a migration, and reads go through `rls_connection` under the table's authenticated-read policy. So
no service-role runtime code was added, which is the tighter and correct choice; noted since it differs from
the framing.
