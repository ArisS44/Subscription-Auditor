# Task 2.12 - Boundary Hardening: Profile Constraints & Fan-Out Cap

## Summary

Both gaps closed. `profiles.renewal_lead_days` and `profiles.monthly_review_enabled` are now `NOT NULL`,
and the lead time carries a `CHECK (>= 0 AND <= 30)` stated identically to the subscriptions constraint it
must agree with. The device reads are bounded on **both** paths — including the service-role one the
reminder job actually uses, which the Task did not name and which was the genuinely unbounded one. 247
tests pass on three consecutive serial runs; no behaviour change.

## Details

**Pre-flight, before writing anything.** Confirmed the Supabase CLI was authenticated *and* linked to
`subscription-auditor-dev` (prod showed `linked: false`), then audited the columns: 16 profile rows, zero
NULLs in either column, zero values outside 0-30 (observed range 3-11). `NOT NULL` is validated against
every existing row as it is applied, so a single offending row would have aborted the migration — the audit
is what made the push safe rather than hopeful.

**Migration** `20260730090000_harden_profile_lead_time_constraints.sql`, applied to **dev only** by the User
via the CLI. Constraint named `profiles_renewal_lead_days_check` to mirror
`subscriptions_reminder_lead_days_check`, so the pair is greppable as one rule expressed twice. Verified
after the fact against the database rather than from the CLI's output: both columns report `is_nullable=NO`
and the CHECK definition is byte-identical to the subscriptions one. `supabase migration list --linked`
shows six migrations with local and remote matching — no drift.

The push emitted a Docker warning ("failed to cache migrations catalog"). That is the CLI failing to build
a *local* catalog cache, which needs Docker Desktop; it is unrelated to the remote apply, which reported
"Applying… / Finished" and is confirmed by the database state above.

**Fan-out cap — and the instruction discrepancy.** The Task said to cap `db/push.py::list_subscriptions`,
justified as "the job-path bounded-work standard". Tracing callers showed that is wrong:

| Function | Caller | Path |
|---|---|---|
| `push.py::list_subscriptions` | `services/push.py::deliver_to_user` | user-initiated, RLS-scoped |
| `reminders.py::get_active_push_subscriptions` | `services/reminders.py` | **the reminder job**, service-role |

The Objective and Validation Criteria say "the reminder fan-out reads at most a bounded number of devices
per user", which is the `reminders.py` function; the Expected Output names `push.py`. **Capped both** — the
Expected Output satisfied literally, the Objective substantively. Capping only the named function would have
looked complete while leaving the externally-triggerable path unbounded. The imprecision originated in my
own Task 2.10 finding, so the correction is mine.

Also added `ORDER BY created_at ASC, id ASC` to the job query, which had none. A `LIMIT` without a total
ordering makes *which* devices survive the cap unspecified, so a user with more devices than the ceiling
could be reminded on a different device each run. The `id` tie-break matters because timestamps collide.

The ceiling is a **separate constant** in each module rather than shared. `db/reminders.py` and
`db/push.py` are deliberately duplicated so service-role reads stay unreachable from user code; sharing
state across that line would start eroding it.

No subagents. No correction loop.

## Validation

- **Rejection comes from the database, not Pydantic.** Every constraint test opens a raw `asyncpg`
  connection — outside the app pool and outside RLS — so the constraint is the only thing able to refuse
  the write. Driving `PATCH /me` would have passed identically against the pre-migration schema, which is
  the definition of a vacuous test.
- **Verified by sabotage, twice.** Dropping `profiles_renewal_lead_days_check` produced
  `Failed: DID NOT RAISE CheckViolationError` plus a second failure from the two-walls test; removing either
  `LIMIT` produced `assert 3 == 2` on both bounding tests and broke the determinism test. All restored and
  re-confirmed green, with the constraint definition checked byte-identical after restoration.
- **Not vacuous in the other direction:** a boundary test asserts 0, 30 and 7 still write successfully — a
  CHECK that rejected everything would satisfy the rejection tests alone.
- **Anti-drift:** one test reads the bound out of the *live* constraint definitions for both tables and
  compares them to `LEAD_DAYS_MIN`/`LEAD_DAYS_MAX`, so changing either wall without the other fails here.
- **Bounded fan-out proven behaviourally**, not by asserting on SQL text: the ceiling is monkeypatched to 2
  against 3 devices and the read returns 2, in the same order twice. Deliberately avoids creating 101 real
  rows on shared dev.
- **Full suite: 247 passed on three consecutive serial runs** (5:50 / 5:46 / 5:45), zero failures. Previous
  baseline 239; the 8 new tests account for the delta exactly. ruff and black clean.
- **No behaviour change:** no API surface, model, or service logic touched. The migration only forbids values
  that could not be produced through the API anyway, and the caps sit far above any real device count.

## Important Findings

**1. The Task's stated rationale attached to the wrong function.** Detailed above. Worth the Manager's
attention because the same reasoning appears in my Task 2.10 log, which is where the error came from: I
described `db/push.py::list_subscriptions` as being "on the reminder job's path" when it is not. Any other
work planned off that finding should be re-read with this correction in mind.

**2. The reminder job's device read had no ordering at all**, which the Task did not mention and which
matters as much as the cap. A bounded-but-unordered read is not deterministic, so a user with more devices
than the ceiling could receive reminders on a different device each run. Fixed here; worth checking whether
any other `LIMIT` in the codebase lacks a total ordering.

**3. Production still needs this migration.** It is applied to dev only. Prod is a separate Supabase project
(`linked: false` at the time of writing) and must receive it via the CLI as part of the deploy — never the
dashboard, per the standing rule after the earlier history desync. This is the last Task before the full app
check and deploy, so it should not be lost.

**4. `docs/LEARNING_LOG.md` previously claimed something untrue.** `backend/app/models/common.py` documents
`LeadDays` as "mirrored byte-for-byte from two DB CHECK constraints" — but the profiles constraint did not
exist until this Task, so the comment described an intention rather than reality. It is now accurate, and a
test enforces it.
