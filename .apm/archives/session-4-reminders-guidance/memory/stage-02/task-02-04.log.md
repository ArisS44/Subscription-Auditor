# Task 2.4 - Service Worker, PWA & Opt-In

## Summary
Implemented browser-side Web Push end to end — service worker, installable PWA manifest, a user-initiated opt-in that registers with the backend, the iOS install surface, and the working onboarding notification step. The desktop path is fully live-verified (subscribe → display → click-focus). Reported **Partial** only because the real-iPhone verification criterion cannot be satisfied now — the User has no iOS device, and iOS Web Push requires HTTPS + Home-Screen install so it can't be exercised on localhost. Everything checkable without a device passes.

## Details
Built in the order taught: service worker model explained first (User confirmed), then each piece incrementally.

- **Service worker** (`frontend/public/sw.js`, plain static JS at root scope): `push` reads the backend's `{title, body, url}` and calls `showNotification` with the Apollo `notification-icon.png` + sun `notification-badge.png`, defensively defaulting a malformed payload; `notificationclick` focuses an existing same-origin window (via `clients.matchAll`, navigating it to the deep link) and only opens a new window when none is found. `install`/`activate` use `skipWaiting`/`clients.claim`. Registered on load in `main.tsx`, and also on demand in the opt-in.
- **Manifest** (`frontend/public/manifest.webmanifest`): `display: standalone`, dark theme/background, `start_url: /dashboard`, icons 96/192/512 `any` + 192/512 `maskable`. Linked from `index.html` with `apple-touch-icon`, `theme-color`, and `apple-mobile-web-app-*` meta. Validated: all required fields present, all referenced icon files exist.
- **Opt-in**: `push-support.ts` (support/iOS/standalone detection, base64url→Uint8Array), `usePushSubscribe.ts` (register → `pushManager.subscribe` with the VAPID public key → POST `/push/subscribe`, reusing an existing browser subscription and SW registration), and `NotificationOptIn.tsx` rendering every state as a clear, non-broken notice: enable / enabling / enabled / blocked / unsupported / error, plus the iOS install hint. Permission is requested on the click gesture; only a grant triggers subscribe.
- **iOS install surface**: numbered Share → Add to Home Screen steps (treatment chosen by the User from three options), shown only on an iOS browser tab (not installed).
- **Onboarding step**: replaced the `notifications` stub (`StubStep`, not `ComingSoonStep` as the prompt said) with `NotificationStep`, gated on `useSubscriptions(..., {limit:1}).total > 0`; when there are no subscriptions it explains why instead; Skip/Continue always advances so declining never blocks completion. Updated the step's `body` copy that still said "coming soon".
- **i18n**: new `notifications.optIn.*` namespace in `en` and `el` at verified full key parity.

## Issues
The dev `POST /push/test` is JWT-authenticated with no UI trigger, so the desktop test fired it via a DevTools console snippet reading the Supabase token from localStorage. Fine for a dev-only check; noted in case a friendlier trigger is wanted later.

## Important Findings
- **iOS real-device verification is outstanding and cannot be done in this environment.** The User has no iPhone, and iOS Web Push requires an HTTPS origin + Home-Screen install (the localhost secure-context exemption does not extend to a `http://` LAN address). The iOS code is complete and all headless checks pass, but on-device push delivery is unproven. Recommend verifying on the **deployed HTTPS build** (Share → Add to Home Screen → open from Home Screen → opt in → fire a test), on any borrowed iPhone/iPad or a cloud real-device service, whenever one is available. This is the sole reason the Task is Partial rather than Success.
- **The notification opt-in currently lives only in the onboarding step.** A user who has already completed onboarding has no way to enable notifications afterwards — the Settings notifications card still shows the disabled "coming soon" switches. Wiring opt-in/opt-out into Settings (and device revocation) was framed as a later Task; flagging that until then, completed users can't opt in. The `NotificationOptIn` component is reusable and can be dropped into Settings when that Task runs.
- **No frontend CSP exists** (the §3 "check, don't assume" point). `staticwebapp.config.json` defines only `navigationFallback`; there is no CSP header there and no `<meta http-equiv>` CSP in `index.html`. The strict `default-src 'none'` CSP is only on the backend API's own responses, which never serve the SW/manifest. So nothing currently blocks the service worker, manifest, or push flow. If a strict frontend CSP is added later it must include `manifest-src 'self'`, `worker-src 'self'`, and `script-src 'self'` (plus `connect-src` for the API) so this flow keeps working.
- Minor prompt/code discrepancies (followed reality): the onboarding stub was `StubStep`, not `ComingSoonStep`; no PWA plugin existed, so the SW/manifest were hand-authored rather than generated.
