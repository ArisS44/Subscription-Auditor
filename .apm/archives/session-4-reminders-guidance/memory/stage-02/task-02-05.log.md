# Task 2.5 - Notification Settings & Lead Time

## Summary
Made the Settings notifications surface real (opt-in, per-user lead time, registered-device list with revocation) and added a nullable per-subscription reminder lead time with a Default/override/clear model. Validated by 131 tests, a clean build, `en`/`el` parity, and live User verification of every criterion.

## Details
- **Notifications card** (`frontend/src/features/settings/NotificationsCard.tsx`, replacing the old disabled stub in `SettingsPanel.tsx`): embeds the `NotificationOptIn` (registering a device *is* enabling reminders — there is no standalone flag, per the model), a per-user lead-time control wired to `renewal_lead_days` via `PATCH /me` (reusing the `setQueryData`-then-invalidate pattern from the onboarding fix), and a registered-devices list (`GET /push/subscriptions`) with per-device revoke (`DELETE /push/subscribe/{encodeURIComponent(endpoint)}`, then re-fetch to confirm server-side deletion). The monthly-review switch stays disabled (`monthly_review_enabled` is read-only) alongside the weekly-summary placeholder.
- **Lead-time control** (`LeadTimeChips.tsx`): presets + custom, the treatment the User chose. Reused on both surfaces; per-subscription it also offers a `Default (N)` option that emits `null`. Per User feedback: chips show just the number (surrounding copy carries "days"), and the inherit option is worded **"Default"** in English (Greek already used «Προεπιλογή»).
- **Per-subscription field**: added `reminder_lead_days` (nullable) to the schema and form. `null` renders as `Default (N)` from the user default; an override persists; clearing returns to `null`. Placed **above** the manage/cancel link so the important field is visible without scrolling (User request).
- **Types**: `Profile` gained `renewal_lead_days` + read-only `monthly_review_enabled`; `Subscription`/create-input gained nullable `reminder_lead_days`.
- **Opt-in reload bug (found in live testing, fixed)**: the "on" state was keyed to a this-session mutation flag, so an already-registered device showed a clickable Enable button after reload. Reworked so enablement is derived from whether this browser's push subscription is in the backend device list (with a brief checking state); `usePushSubscribe` now invalidates the device list. This also flips the opt-in back off correctly after a revoke.

## Important Findings
- **The chatbot (Apollon) made an ungrounded, unconfirmed subscription edit — a chat-surface defect surfaced while testing this Task.** Asked (in Greek) to "change how often" reminders come for a subscription, the assistant (1) set `reminder_lead_days` to a specific value (5) the User never gave, (2) silently matched "Pokemon golf" → an existing "Pokemon go" as if certain, and (3) applied the mutation without confirming target or value. This is the chat tool-calling surface (backend/chat agent), **not** this Task — my work only made the backend field the chat's update tool can now write. Recommend routing to the chat-agent owner: a mutating subscription-edit tool should confirm an ambiguous name match and never fabricate a numeric value; when a value isn't supplied it should ask, not guess. Flagged so the field this Task exposed is not written carelessly through chat.
- **Prior-Task follow-through completed:** this Task carried out the "opt-in only lived in onboarding" item flagged in Task 2.4 by embedding `NotificationOptIn` in Settings. The remaining 2.4 item (iOS on-device verification) is still outstanding and unrelated to this Task.
- **User interest noted:** the User asked whether a subscription can have more than one reminder. The current model supports only a single `reminder_lead_days` per subscription; multiple reminders would need a backend model change (array or separate table) and reminder-engine work. Not built; raised in case the Manager wants to scope it.
