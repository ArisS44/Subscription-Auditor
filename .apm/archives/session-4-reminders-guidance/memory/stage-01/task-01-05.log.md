# Task 1.5 - Test Fixture Rework

## Summary

Replaced per-test Supabase user creation with two session-scoped shared users plus an unconditional
per-test row reset, taking a full run from 74 real users / 222 Auth Admin round-trips to 2 / 6. Three
consecutive full runs came back 140 passed / 0 failed, against a measured baseline of 1, 2 and 0 failures.

## Details

**Baseline measured first (step 1), and the Manager's estimate was low.** The prompt estimated 64 test
functions across 11 files and ~128 round-trips. Actual: 137 tests across 15 files, with 64 uses of `user_a`
and 10 of `user_b` — 74 users, and 222 round-trips once the three calls per user (admin create, password
grant, admin delete) are counted. The "64" coincidentally matched the `user_a` count rather than the test
count. Measured via `pytest --collect-only --fixtures-per-test`, and `conftest.py` confirmed as the only
user-creating path.

Baseline failure counts across three consecutive runs: **1, 2, 0** — with a different test failing each
time (`test_chat.py::test_cap_breach_degrades_without_calling_llm`,
`test_chat.py::test_grounded_render_is_stored`, `test_fx.py::test_convert_endpoint_rejects_bad_currency`),
two of them `AuthError`. Notably milder than the 8 failures seen during Task 1.1 the previous day, which is
itself evidence of how load-dependent and non-reproducible the signal is.

**Design (step 2).** Chose a session-scoped pool of two users with a per-test reset. Rejected: dropping the
delete call (cuts round-trips by a third, trajectory unchanged); sharing without cleanup and hardening tests
against leftover rows (that is loosening assertions); and local Supabase in Docker, which is the better
long-term answer but is a dev-environment change beyond this Task, and the Docker daemon is not running on
this machine.

Two non-obvious design points. Cleanup runs on **setup, not teardown** — teardown-only cleanup is skipped by
a test that errors part-way, which would surface as an unrelated later test failing. And cleanup uses its
**own short-lived connection** rather than the app pool, because the `db_pool` fixture opens and closes that
pool around individual tests; connecting directly also runs without the `authenticated` role, bypassing RLS,
which is required for cleanup to delete rows across both users.

Cleanup covers `messages`, `conversations`, `notification_deliveries`, `push_subscriptions`, `subscriptions`
and `llm_usage`, then resets `profiles` field-by-field to signup defaults. `llm_usage` was included because
`test_chat.py` already hand-cleans it after nearly every test — the daily-cap tests would otherwise find a
budget earlier tests had spent. The profile row is trigger-created at signup so it is reset rather than
deleted; `PATCH /me` tests mutate it.

**Verification (step 5) is the substantive result.** RLS was disabled on all six user-scoped tables and the
denial tests re-run: **all six failed**, with the assertion output showing an actual leaked row (user B's
subscription visible to A). This proves they detect a loss of denial rather than passing vacuously. RLS was
restored via an EXIT trap and then independently verified enabled on all nine public tables via `pg_tables`.
A structural guard was also added: `test_rls.py::test_cross_user_read_denied_by_rls` was the one denial test
that did not first confirm the target row existed, so a positive control was added. `test_chat_rls.py` and
`test_notification_rls.py` already had one.

One correction loop: `loop_scope` is not accepted by `pytest.fixture`, only by `pytest_asyncio.fixture`.
Fixed directly, no subagent needed. No other test required adjustment — the 137 existing tests passed
unchanged on the first full run after the rework.

## Compatibility Concerns

**The suite must now stay serial.** Two users shared across parallel workers would reintroduce exactly the
cross-test interference the reset exists to prevent — worse, one worker's cleanup would delete another
worker's rows mid-test. `pytest-xdist` cannot be adopted without revisiting this design (per-worker user
pairs would be the fix). Nothing currently runs the suite in parallel, and CI should not start doing so
without that change. Recorded in `docs/DECISIONS.md`.

**Two Supabase users now persist for the duration of a run** rather than existing for a single test. They are
still deleted at session end, but a hard-killed run (SIGKILL, CI timeout) will leave two orphaned test users
in dev auth rather than none. Low impact, worth knowing.

## Important Findings

**The flakiness signal is far noisier than a single measurement suggests.** Task 1.1 saw 8 failures in one
run; the baseline here, on the same code four days later, produced 1, 2 and 0. Anyone judging this problem —
or judging whether a future change caused a regression — from one run will reach a confident wrong
conclusion. This is a reason to keep the three-run protocol for any future change touching the fixtures.

**Local Supabase in Docker remains the better long-term answer and is now the only remaining lever.** This
Task removed the rate-limit pressure from user *creation*, but the suite still runs against shared dev, so it
remains exposed to a concurrent run from elsewhere and to any other rate limit Supabase applies. The Task
Prompt itself notes a concurrent run is possible. Running Supabase locally would eliminate the shared-resource
dependency entirely rather than economising on it. It is a dev-environment decision for the Manager, not
something to adopt inside a test Task.

**A latent hazard now exists that did not before.** With shared users, any *future* test that deletes its
user, or that relies on a user having never existed before, will break in a way that is confusing to diagnose
— and any future user-scoped table must be added to `_reset_user_data` or it will silently leak rows between
tests. That second one is the real trap: forgetting it produces cross-test contamination rather than an
obvious error. Worth stating in whatever guidance covers the mandatory RLS-test rule, since the two now
interact.
