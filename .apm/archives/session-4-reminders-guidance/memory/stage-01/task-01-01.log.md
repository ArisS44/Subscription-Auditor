# Task 1.1 - Notification & Guidance Schema

## Summary

Created `push_subscriptions`, `notification_deliveries`, and `service_guides` plus the
`subscriptions.reminder_lead_days` column in one migration, applied to dev with no history drift, and proved
RLS and the ledger's idempotency constraint with six real-DB tests. All validation criteria met.

## Details

Relinked the Supabase CLI from prod (`ylwjevannrlsauegwbas`) to dev (`zocfhyysnvptxktqezfk`) and confirmed
authentication separately before any write; verified migration history matched local/remote both before and
after the push. Nothing was applied to production.

Read the three existing migrations and matched their conventions (lowercase DDL, `check` over Postgres enums,
four-policy RLS for user-scoped tables, commented rationale). Modelled `service_guides` on `fx_rates`, which
lives inside `20260710091357_create_chat_schema.sql` rather than in a migration of its own.

Two design decisions were made beyond what the Task Prompt specified:

1. **`subscription_id` is nullable, and the unique constraint uses `NULLS NOT DISTINCT`.** The prompt states a
   `monthly_review` kind is coming in a later session; that kind is account-wide and has no subscription to
   reference, so the column must be nullable. Under Postgres' default `NULLS DISTINCT`, two monthly-review
   rows with `subscription_id = NULL` would count as different keys and both would be accepted — the
   deduplication would silently fail for exactly the kind that needs it. `unique nulls not distinct`
   (Postgres 15+) closes this; the precedent is `llm_usage_scope_day_uniq` in the chat schema migration. A
   dedicated test covers the NULL case.

2. **Added `subscriptions_active_next_renewal_date_idx`**, a partial index on `next_renewal_date` where
   `status = 'active'`. The prompt asked me to consider whether the reminder scan warranted an index. It does:
   the job scans renewals across all users and has no `user_id` to filter on, so every existing subscriptions
   index (all of which lead with `user_id`) is unusable for it. The partial predicate keeps the index small by
   excluding cancelled/paused rows the job never considers.

`reminder_lead_days` carries a `CHECK (>= 0 AND <= 30)` sanity range. No backfill was needed or performed —
NULL already means "inherit `profiles.renewal_lead_days`", so pre-existing rows are correct as they stand.

Tests were written inline-SQL rather than through db-layer helpers, following `test_chat_rls.py`, so as not to
pre-empt db modules later Tasks will own. Learning-log entries were added for the ledger/uniqueness concept,
the `NULLS NOT DISTINCT` gotcha, the reference-data RLS shape, and the nullable-means-inherit pattern.

No subagents were needed; no correction loop was entered (the only iteration was a 101-character line caught
by ruff).

## Validation

- **Migration applies cleanly to dev, no drift:** `supabase migration list` before the push showed three
  migrations with `local == remote`; after, four with `local == remote` including `20260722143000`. A Docker
  warning appeared ("failed to cache migrations catalog") — this concerns only local catalog caching, not the
  push, which reported success.
- **Cross-user denial:** asserted for SELECT, UPDATE, and DELETE on both user-scoped tables, plus a follow-up
  assertion that user A's row is unchanged after B's attempts.
- **`service_guides` read-only to users:** read succeeds; INSERT raises `InsufficientPrivilegeError` and
  UPDATE/DELETE match zero rows. Both are denial, in the two different shapes RLS produces.
- **Ledger uniqueness:** a duplicate `(user_id, subscription_id, kind, due_date)` insert raises
  `UniqueViolationError`, asserted directly; a different `due_date` is still accepted, so the constraint does
  not suppress legitimate future reminders.
- **`reminder_lead_days`:** defaults to NULL on a fresh row, `coalesce` resolves to the profile default of 3
  when NULL and to the override when set, and an out-of-range value raises `CheckViolationError`.
- **Suite:** 137 tests, 129 passed / 8 failed on the full run. All 8 passed on isolated rerun (the 6 new tests
  as a file; the 6 pre-existing failures as an explicit selection), confirming them environmental. Ruff and
  black clean; pre-commit hooks passed.

## Important Findings

**The shared-dev test flakiness is escalating and is close to obscuring real failures.** The Task Prompt
documents 1–3 intermittent live-DB failures per full run; this run produced **8**, spanning
`test_analytics`, `test_chat`, `test_subscriptions`, `test_tools`, and two of the new tests, with
`AuthError: Invalid authentication credentials` as the dominant signature. The cause is the known one — Auth
Admin rate limiting and pooler drops under back-to-back test-user creation — and this Task made it worse by
design: six new live-DB tests each mint one or two real Supabase users via the Auth Admin API, and every
future user-scoped table adds more under the project's own mandatory RLS-testing rule.

The two effects compound. The rule that every user-scoped table needs a real cross-user denial test is correct
and should stay, but it guarantees the user-creation rate climbs with each Task, while the tolerance for
"acceptable" flaky failures climbs with it. At 8 failures per run, the practice of confirming failures by
isolated rerun still works but costs a full extra cycle; at a higher count, a genuine regression becomes easy
to wave through as environmental. This is a test-infrastructure decision (session-scoped shared fixture users,
throttling user creation, or a local Supabase instance for the suite) rather than something to solve inside a
schema Task, so it is raised rather than acted on.

**Minor prompt discrepancy.** The prompt directs finding "that migration" for `fx_rates` as though it were
standalone; `fx_rates` is defined inside `20260710091357_create_chat_schema.sql`. No impact — the pattern was
found and followed.
