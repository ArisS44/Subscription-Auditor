# Task 1.3 - VAPID & Job Token Provisioning

## Summary
Generated a Web Push VAPID keypair and a 384-bit scheduled-job token, provisioned them across local
development, Azure Key Vault, the Container App, and GitHub Actions, and extended backend configuration
and both `.env.example` templates. No secret value appears in any tracked file.

## Details

**Deviation from the Task Prompt (see Important Findings).** The prompt stated neither secret existed.
The job token was indeed absent, but the VAPID *variables* were already declared in
`backend/app/config.py`, both `.env.example` templates, and `.github/workflows/frontend.yml`. The
plumbing existed; only the values were missing. Followed the actual codebase state rather than
re-adding existing declarations, per the Instruction Accuracy clause.

**Teaching.** Delivered the required VAPID explanation before any generation: what the keypair proves
(provenance of the sender, not authorisation), why a leaked endpoint URL is inert without the private
key, why one application-wide keypair is the correct granularity, why the public half is safe in a JS
bundle, and the scope limit that VAPID protects the endpoint while payload confidentiality is the
separate per-subscription `p256dh`/`auth` mechanism. The User asked the Agent to answer its own
comprehension questions rather than answering them; complied and proceeded.

**Generation.** Wrote a script (scratchpad, not committed) using `cryptography` 49.0.0, already present
in `backend/.venv` as a transitive dependency of `pyjwt[crypto]` - no new dependency, no network call,
no third-party CLI handling the key. It writes directly into the gitignored env files and prints only
the public key, so the private key and job token never entered the clipboard, terminal scrollback, or
chat. Chose this over `npx web-push generate-vapid-keys` to keep key material entirely local. Refuses
to overwrite populated values without `--force`, since re-running would rotate the keypair and
invalidate every existing push subscription. Verified lengths: public 87, private 43, token 64.

**Cloud provisioning (User-executed).** All `az` commands prepared, explained, and run by the User.
Used `-o none` throughout because `az keyvault secret set` returns the secret value in its JSON output
by default. `az containerapp secret set` warned a restart was required; the following
`containerapp update --set-env-vars` satisfied it by creating a new revision.

**Distribution asymmetry**, deliberately different per secret:

| Secret | Key Vault | GitHub Actions | Rationale |
|---|---|---|---|
| VAPID private key | `vapid-private-key` | - | nothing in CI signs a push |
| VAPID subject | `vapid-subject` | - | contact URI in the signed JWT |
| VAPID public key | - | `PROD_VITE_VAPID_PUBLIC_KEY` | not secret; Vite needs it at build time |
| Job token | `job-token` | `PROD_JOB_TOKEN` | shared secret: backend verifies, workflow sends |

All three Container App secret aliases fit under the 20-character cap, so no shortening was needed
(unlike the existing `sb-service-role-key` and `chat-global-cap`).

## Important Findings

**1. The Task Prompt's premise was partly stale.** VAPID configuration plumbing already existed from
earlier sessions (`config.py`, both templates, and `frontend.yml:24` already referencing
`PROD_VITE_VAPID_PUBLIC_KEY`). Only values were missing. Tracked changes were therefore smaller than the
prompt anticipated - effectively the job token alone. Worth noting that `frontend.yml` has been
injecting an empty string for `VITE_VAPID_PUBLIC_KEY` into every production frontend build since that
line was added; it now has a real value.

**2. The VAPID keypair is provisioned but unproven.** Nothing sends a push yet, so this Task establishes
that the values are correctly placed, not that they work. Per the project standard on work that cannot
be verified locally, real confirmation requires the push sender plus a live browser subscription on
HTTPS receiving a notification. The Task that builds the sender should treat live device verification as
a required step, not a formality - a wrong key encoding would pass every check performed here.

**3. `JOB_TOKEN` defaults to `""` and the consuming endpoint must fail closed.** The empty default keeps
local dev and the test suite runnable and matches how `vapid_*` and the optional LLM settings are
declared. It is only safe if the endpoint treats "unset" as deny rather than "no token required" -
otherwise a misconfigured deployment leaves a publicly routable endpoint unauthenticated. This is a
direct constraint on the Task that builds the scheduled endpoint, and is recorded in the `config.py`
comment and the learning log.

**4. Rotation now has a two-place invariant.** The job token must stay identical in Key Vault and GitHub
Actions; rotating one alone silently breaks every scheduled run with no error until a run is due.
Documented in `infra/azure/README.md` §4.

**5. `az keyvault secret set` prints the secret back by default.** Its JSON output includes `value`, so
provisioning without `-o none` leaves every secret in shell scrollback. Recorded in the infra README and
learning log; relevant to any future Task provisioning secrets.
