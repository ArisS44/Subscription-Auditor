   with `vi.fn(() => ...)` — no parameter types — so TypeScript inferred `mock.calls` elements as the
   empty tuple `[]`, and `tsc -b` (which runs before `vite build`, and type-checks test files) rejected
   `call[0]`/`call[1]` indexing (TS2493) and the `undefined`→`RequestInit` cast (TS2352). `vitest run`
   passed because Vitest records real args at runtime, so the `test` step was green while `build` failed
   — the gap only surfaces in CI's build, which never ran on the feature branch (workflows fire on push
   to `main`). Fixed by typing both mocks via `vi.fn<typeof fetch>` (matching the existing
   `ChatView.test.tsx` fetch-mock convention), giving `mock.calls` the real `[input, init?]` tuple.
   Verified locally with the exact CI command (`npm run build`) plus lint and the onboarding tests
   (20/20) before re-pushing. Committed `0312e4f`.
4. **Both pipelines green.** Backend CI/CD #3 (`9d899ce`) green (tests → image build/push → Container App
   update). Frontend CI/CD #5 (`0312e4f`) green (build with real `PROD_VITE_TURNSTILE_SITE_KEY` → SWA

## Important Findings
- **`tsc -b` vs `vitest` coverage gap (recurs).** CI's `npm run build` runs `tsc -b`, which type-checks
  **test files**, while `npm run test` (Vitest) does not enforce full project type-checking. A type error
  confined to a test file passes `test` but fails `build` — and since the workflows only run on push to
  `main`, this isn't caught until deploy. Mitigation for future frontend work: run `npm run build`
  locally (not just `npm run test`) before merging test-file changes. Worth a Worker rule if this recurs.
- **Node 20 deprecation warning in CI.** Both workflows use actions (`actions/checkout@v4`,
  `astral-sh/setup-uv@v3`) that still target Node 20; GitHub is force-running them on Node 24 and will
  drop Node 20 support. Non-blocking now, but a near-term maintenance item (bump action versions).
- **Turnstile key-slot mix-up during 3.1 was corrected before any exposure** (context carried from the
  prior Task): the private secret key briefly sat in the GitHub site-key secret, was moved before any
  workflow consumed it, and the live check here confirms the real *site* key is what shipped to the
  browser — so no private-key leak occurred.
