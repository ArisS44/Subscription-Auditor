# Task 3.1 - Secrets & Production Migration

## Summary
Provisioned all Session-3 production infrastructure: relinked the Supabase CLI to prod and applied the
chat-schema migration, set the four new LLM/chat-cap secrets in Key Vault and wired them through the
Container App (new revision boots healthy), and provisioned real Cloudflare Turnstile for prod (site key
as a GitHub secret wired into `frontend.yml`, secret key in the Supabase Auth CAPTCHA setting). All
external, real-credential steps were User-driven; each was verified.

## Details
Executed as an ordered, User-driven sequence with a verification gate after each step:

1. **Supabase relink to prod.** CLI was linked to dev (`zocfhyysnvptxktqezfk`) as expected. User ran
   `supabase link --project-ref ylwjevannrlsauegwbas`; `supabase projects list` confirmed the ● marker
   moved to `subscription-auditor-prod`.
2. **Migration push.** `supabase db push` needed `supabase login` (access token) in addition to the link
   — the documented friction. `--dry-run` showed exactly one pending migration
   (`20260710091357_create_chat_schema.sql`) and **no** history mismatch, so no `migration repair` was
   needed (prod history was already reconciled). The Docker warning during push was harmless (only the
   local migrations-catalog cache, unrelated to the remote push).
3. **Key Vault secrets + Container App wiring.** Set `llm-provider`, `llm-model`, `llm-api-key`,
   `chat-global-daily-cap` in `kv-subaudit-prod`. Wired each as a Container App secret reference then an
   env var. **Alias-cap correction:** `chat-global-daily-cap` is 21 chars, over the Container App
   secret-key 20-char cap, so its Container App alias is `chat-global-cap` (the Key Vault secret keeps the
   full name), mirroring the README's `sb-service-role-key` precedent. The env-var update created a new
   revision that came up `Running`; `/api/v1/health` → `{"status":"ok"}` and `/api/v1/ready` →
   `{"status":"ok","database":"up"}`.
4. **Turnstile.** Wired `VITE_TURNSTILE_SITE_KEY` into `frontend.yml` from a new
   `PROD_VITE_TURNSTILE_SITE_KEY` GitHub secret. User created a Cloudflare Turnstile widget scoped to the
   SWA default hostname (`red-tree-0557d7c03.7.azurestaticapps.net`), added the **site key** as the GitHub
   secret, and pasted the **secret key** into the prod Supabase Auth → Attack Protection CAPTCHA setting
   (enabled + saved). A brief key mix-up (secret key initially entered as the GitHub secret) was corrected
   before any workflow ran, so nothing was baked into a bundle or logged.

Committed the two tracked-file changes on `feat/prod-secrets-and-migration` (`9d899ce`).

## Important Findings
- **Turnstile is provisioned but not yet live in the browser.** The site key is stored and `frontend.yml`
  is wired, but Vite bakes it in at build time — production keeps shipping the always-passing *test* key
  until the frontend is rebuilt and redeployed (Task 4.2's frontend pipeline, or a manual
  `workflow_dispatch`). CAPTCHA is not actually enforcing on the live site until that redeploy happens.
- **Container App secret-key 20-char cap bites again.** `chat-global-daily-cap` needed the shorter
  Container App alias `chat-global-cap`; any future secret whose name exceeds 20 chars needs the same
  alias treatment (README updated to record this).
- **Gemini key handling.** Only `llm-api-key` and `chat-global-daily-cap` are strictly load-bearing;
  `llm-provider`/`llm-model` merely pin the code defaults and were set per the Task and the
  config-from-environment rule. Recorded in `infra/azure/README.md` for future tasks.
