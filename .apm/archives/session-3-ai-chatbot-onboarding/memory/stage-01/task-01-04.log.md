# Task 1.4 - Chat SSE Endpoint, Conversation Loop, Persistence & Caps

## Summary
Built the full Apollon chat engine: conversations CRUD + an SSE `POST
/conversations/{id}/messages` endpoint, the tool-calling loop over the registry, message/conversation
persistence, auto-titling, inline-visual grounding, and the DB-backed cap set with graceful degradation.
Validated with 11 stubbed-LLM integration tests plus a real-model end-to-end smoke.

## Details
- `routers/chat.py`: conversations list/get/create/delete + SSE message endpoint. All routes go through
  `rls_connection(claims)`; the SSE endpoint pre-checks ownership (clean 404) then returns a
  `StreamingResponse` (`text/event-stream`) with `Cache-Control: no-cache` and `X-Accel-Buffering: no`.
  Events are `data: {json}\n\n` frames (delta/tool/structured/title/done/error). Registered in `main.py`.
- `services/chat.py::stream_turn`: caps → ownership + persist user message + load a bounded ~20-message
  replay window + read `preferred_language` → loop: `llm.stream_chat_turn(history, tools.tool_definitions(),
  system=build_system_prompt(...))`, stream text deltas, dispatch each `ToolCall` via `tools.dispatch`
  (never a handler directly), feed results back, cap at `chat_max_tool_iterations` (5). Persists
  user/assistant(tool_calls)/tool(tool_call_id)/final-assistant rows; stores a grounded render payload in
  `structured_payload`. Grounding: a `render_chart`/`render_table` payload is accepted only if
  `get_analytics` ran in the same turn. Auto-titles the first message via `llm.generate_title`.
  Destructive confirmation is left to the prompt — the loop adds no second mechanism.
- Caps: `services/usage.py` + `db/usage.py`. Per-user 30/min (count of the user's own messages in a 60s
  window), 200/day, and a tunable app-wide daily ceiling (default 5000) via `llm_usage`
  upsert-increment on a **service-role** connection (llm_usage has read-own RLS only, no write policy). A
  breach returns a graceful degraded event; the LLM is never engaged.
- `db/chat.py`: conversations/messages persistence with JSONB `tool_calls`/`structured_payload`
  (json.dumps/loads at the boundary). `models/chat.py`: added `ChatMessageRequest` (content cap +
  onboarding flag). `config.py`: 5 tunable chat settings.

## Important Findings
- **Provider function-calling rejects Pydantic's Decimal JSON-schema.** Tool `parameters` derived directly
  from a Pydantic model with a `Decimal` field emit a string-branch `pattern` regex using lookahead
  `(?!…)`, which Groq's RE2-based validator rejects → HTTP 400 for the entire request (caught only by the
  live check, not the stubbed tests). Fixed with `_provider_safe_schema` in `tools.py`, which recursively
  strips `pattern`/`format` before the schema is sent; safe because `tools.dispatch` re-validates every
  payload against the real Pydantic model. **Any future tool argument model with a `Decimal`/regex-pattern
  field is covered by this sanitizer** — but if a new provider adapter is added, keep this in mind. This is
  a concrete example of why the live-validation step matters on LLM surfaces.
