# Task 1.6 - Chat Engine Quality & Grounding Fixes

## Summary
Fixed all three live-observed chat defects — a fabricated write, an internal tool-name leak, and the
turn-2 HTTP 413 — and verified them against the real Groq model in a multi-turn conversation. The 413 was
root-caused to Groq's free-tier token-per-minute budget (not outbound bloat) and is now handled gracefully.

## Details
Investigated each symptom before changing anything.

- **Symptom 1 (fabricated add):** required fields on `SubscriptionCreate` are already strict
  (`name`, `price`, `billing_cycle`, `start_date`); no schema change stops a determined hallucination of
  free-text values, so the fix is prompt discipline. Added an "action integrity" rule to the shared
  `_APOLLON_IDENTITY` block: never claim a write happened without a real successful tool result; ask for
  missing required details, never invent a placeholder value.
- **Symptom 2 (tool-name leak):** added an "internal mechanics stay hidden" rule — never name/quote/suggest
  a tool or "command"; the user only sees natural language. Both fixes land in the shared identity block so
  the standard and onboarding variants can't drift.
- **Symptom 3 (413):** measured the outbound request empirically — full tool-schema envelope is ~9KB,
  correctly sanitized (no `pattern`/`format`), and a realistic turn-2 payload is ~9.5KB (~2.4K tokens) and
  returns HTTP 200. So the "schema resent / history duplicated / prompt too large" hypotheses are all
  **disproven**. Reproducing against live Groq showed the 413 is Groq mapping a **token-per-minute rate
  limit** (`limit_tokens=12000` for `llama-3.3-70b-versatile` on the free `on_demand` tier; 100K/day) to
  HTTP 413 ("Request too large ... on tokens per minute (TPM)"), and 429 for the daily budget. The defect in
  our code was surfacing this as an opaque `"LLM provider returned HTTP 413"` StreamError (which also leaks a
  provider status). Fix: the adapter now detects 413/429 and yields `StreamError(reason="rate_limited")` with
  neutral user copy; `chat.py` propagates the reason to the SSE error event.

Live re-verification against the real model: (1) bare "I want to add a subscription" → the model asks for
name/price/billing/start date, calls no tool, creates nothing; (2) "how do I see my subscriptions" → natural
answer, no tool name in text; (3) a paced 3-turn conversation staying under TPM → no 413. A burst of
back-to-back turns did hit the TPM limit — and now degrades cleanly as `rate_limited`, confirming the fix.

## Compatibility Concerns
- New SSE error `reason="rate_limited"` is a value the Frontend chat UI (Task 2.1) should recognize and show
  as a friendly retriable state (distinct from `llm_error`). The generic non-rate-limit error message was
  also changed from a raw HTTP status to "The assistant is temporarily unavailable."
- `StreamError` gained a `reason` field with a default — additive, backward-compatible.

## Important Findings
- **Provider capacity is a real constraint, and a decision is pending.** Groq's free `on_demand` tier caps
  `llama-3.3-70b-versatile` at 12,000 tokens/minute and 100,000/day. Because each chat turn can fire several
  tool-loop iterations (each resending system + history + all tool schemas), a handful of quick turns
  exhausts the per-minute window and the next turn 413s regardless of its own size — which is exactly the
  reported bug. Graceful handling is now in place, but the underlying limit makes real multi-user testing
  painful. Recommend a Manager decision: upgrade to a paid tier, or migrate provider (the User is leaning
  toward Gemini Flash on a ~€10 budget, or Claude Haiku 4.5). The `llm.py` adapter already makes this a
  config + one-adapter change; the friction is (a) Gemini's stricter function-calling schema likely needs
  `_provider_safe_schema` extended for `anyOf`/`$ref`, and (b) a new sub-processor requires a Privacy Policy
  update (GDPR).
- **Distinct model glitch discovered (affects Frontend Task 2.1).** Live, Llama-3.3-on-Groq occasionally
  emits a tool call as literal text (`<function/render_table>{...}</function>`) instead of using the
  tool-call channel. This is separate from Symptom 2 (conscious tool-name references, which the prompt fix
  resolves) — it's a model-behavior glitch. Not fixed here (out of scope); worth a display-layer sanitizer
  guard and/or provider change. Flagging so it isn't mistaken for a Symptom 2 regression.
- **Prompt is not yet exhaustively validated.** Live checks covered the three reported cases plus a few
  adjacent ones; a systematic pass (adversarial gap-filling, both languages, onboarding vs standard,
  prompt-injection resistance) has not been done and the User has asked for it.
