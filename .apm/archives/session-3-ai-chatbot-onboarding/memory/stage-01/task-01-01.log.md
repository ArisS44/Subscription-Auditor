# Task 1.1 - Migrations, Models & manage_url API

## Summary
Created and dev-applied the chatbot schema (conversations, messages, fx_rates, llm_usage, plus
subscriptions.manage_url) with RLS on every user-scoped table, added the conversation/message Pydantic
models, threaded an http(s)-validated manage_url through the subscription models/db/service, and proved
cross-user RLS denial for the chat tables. All targeted validations pass against dev.

## Details
- Wrote one migration `supabase/migrations/20260710091357_create_chat_schema.sql` covering all five
  schema items, mirroring the existing migrations' commenting and RLS style.
  - `conversations` / `messages`: four-policy `auth.uid() = user_id` RLS. `messages.conversation_id`
    is `on delete cascade` (GDPR-alignment: deleting a thread deletes its messages), plus the required
    `(conversation_id, created_at)` history index and a `(user_id, updated_at desc)` list index on
    conversations.
  - `messages.role` is a CHECK constraint (`user|assistant|tool|system`), matching the project's
    convention of CHECK over Postgres enums; kept byte-identical to the Literal in `models/chat.py`.
  - `fx_rates`: global reference data, RLS enabled with a single `to authenticated ... using (true)`
    read policy and no write policy (writes go via the service role, bypassing RLS). Unique `(base,
    quote)` for upsert-latest. No `service_guides` table existed to mirror, so the policy was designed
    from Supabase's standard authenticated-read shape.
  - `llm_usage`: DB-backed daily counters. `user_id` NULL = app-wide counter; keyed with
    `unique nulls not distinct (user_id, day)` (Postgres 15+) so there is exactly one row per (scope,
    day) and the future counter service can upsert with a single ON CONFLICT target. RLS own-row read
    only; writes via service role.
  - `subscriptions.manage_url`: nullable TEXT; format/length validated at the API boundary only
    (display-only link, never fetched → no SSRF surface).
- Added `backend/app/models/chat.py` (Conversation + Message create/response/list models, `MessageRole`
  Literal, length caps) following `subscription.py` conventions.
- Added a reusable `ManageUrl` annotated type (BeforeValidator: length cap then `AnyHttpUrl`) to
  `subscription.py`; added `manage_url` to `SubscriptionCreate`/`Update` (constrained) and
  `SubscriptionResponse` (loose str, matching how `currency` is handled). Threaded it through
  `db/subscriptions.py` (`_COLUMNS`, `insert_subscription`, `_UPDATABLE_COLUMNS`) and the create service.
- Added `backend/tests/test_chat_rls.py` (cross-user read/modify/delete denial for conversations and
  messages via inline SQL through `rls_connection` — deliberately not a new db-layer module, to avoid
  pre-empting the chat db layer a later task owns) and manage_url round-trip + 422 tests in
  `test_subscriptions.py`.

## Important Findings
- **Full-suite test flakiness against shared dev Supabase.** Running the entire backend suite
  (`pytest -q`, ~77s) intermittently fails one test — a *different* test each run
  (`test_list_filter_by_category` once, `test_analytics::test_active_only_...` the next), both in
  pre-existing files unrelated to this task. Each failing test passes deterministically in isolation and
  in the 25-test targeted run. Root cause is the shared dev pooler dropping/refusing connections under
  the full suite's load (dozens of user creations + many pooled connections), surfacing as a non-200
  (`KeyError: 'items'`). This is environmental, not a regression from this task, but the Manager should
  know the full suite is not currently reliable as a single-shot gate — consider a connection-pool/retry
  or serialization tweak, or running heavy DB tests in smaller batches, before relying on it in CI.
- The Supabase CLI required `supabase login` (access token) in addition to the relink; the User was
  logged out. `supabase db push` (Management API) needs the token even though `supabase link` did not.
- `supabase db push` emitted a non-fatal Docker warning ("failed to cache migrations catalog"); the
  remote migration still applied. Docker is only needed for local catalog caching / `db diff`, not for
  pushing to the remote.
